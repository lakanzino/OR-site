# مرحلهٔ ۵.۲۶ — شبیه‌سازی پاسخ ازدست‌رفته پس از ذخیرهٔ واقعی

در ادامهٔ آزمون Chromium احرازشده به WordPress/MariaDB دورریختنی، یک wrapper صرفاً در browser test، پاسخ موفق واقعی endpoint را پس از دریافت کامل و ثبت آن دور می‌اندازد و برای JS محصول خطای ساختگی ایجاد می‌کند. آزمون باید نشان دهد snapshot و نام واقعاً ذخیره شده‌اند، صفحهٔ اصلی نتیجه را نامعلوم و دکمه را قفل می‌بیند و submit دوم همان صفحه ارسال نمی‌شود. سپس در صفحهٔ تازه با همان کوکی، revision و محتوای ذخیره‌شده دوباره رندر و **از بین رفتن قفل محلی** ثابت می‌شود؛ صفحهٔ جدید خودکار درخواست مجدد نمی‌فرستد.

ایدهٔ جداکردن commit از رسید پاسخ از [بحث Stack Overflow](https://stackoverflow.com/questions/31970960/how-to-safely-retry-a-failed-jquery-ajax-post-request) و [بحث GitHub Stripe](https://github.com/stripe/stripe-ruby/issues/431) گرفته شده است. این قطع واقعی شبکه یا قطع وسط COMMIT نیست: handler HTTP تا انتها اجرا و پاسخ کامل در لایهٔ تست مصرف شده است. صفحهٔ تازه proof عملیات در حال اجرا یا attribution قطعی نیست. در سناریویی دیگر درخواست می‌تواند پس از بازخوانی هنوز در حال اجرا باشد؛ این آزمایش مدعی حل آن نیست.

فقط fixture و تست‌ها تغییر کرده‌اند؛ idempotency، وضعیت نامعلوم پایدار، اتمی‌بودن کل فرم، migration، writerهای مستقل، OAuth/ACF و سایت هدف بازند؛ **۷۵٪ ثابت** و NO-GO عمومی پابرجاست. نتیجهٔ CI روی commit `17f2e2a`: [رزرو 42416162949](https://github.com/lakanzino/OR-site/actions/runs/42416162949) و [MariaDB 42416163047](https://github.com/lakanzino/OR-site/actions/runs/42416163047) موفق؛ step آزمون backend واقعی نیز موفق. کد افزونه و ZIP همان ۰٫۳٫۴۷ است؛ PR پیش‌نویس است و نصب یا merge انجام نشده است.
