# انتشار و آزمون اولیهٔ محدود نوبت‌دهی روی live — تصمیم مدیر

**تصمیم ۶ نوامبر ۲۰۲۶:** مدیر با اعلام داشتن بکاپ کامل و کم‌ترافیک بودن سایت، ریسک سه بدهی فرم را برای تست اولیه پذیرفته و ادغام و Release را خواسته است. این تصمیم **GO برای انتشار و آزمون اولیهٔ محدود توسط خود مدیر** است، نه اثبات نبود ریسک یا رفع بدهی‌ها. استفادهٔ عمومی از نوبت‌دهی هنوز تأیید نشده است. ایجنت هیچ سایت زنده‌ای را باز، نصب یا تغییر نداده؛ بکاپ و restore توسط او تأیید نشده‌اند.

## بسته و به‌روزرسانی

- افزونه: `0.3.22`، بستهٔ نصبی [`hamyar-doctors-0.3.22.zip`](../../releases/hamyar-doctors-0.3.22.zip)، SHA-256: `8caa90f14ec66f143612e517f1cf25ab8cb5ec5400cc950a7db1ed4666f37850`. قالب در این تغییر دست نخورده است.
- Release: `doctors-v0.3.22`. نسخهٔ ۰٫۳٫۲۲ در header و ثابت افزونه وجود دارد. **صرف Release نمایش آپدیت افزونه در وردپرس را تضمین نمی‌کند**: به‌روزرسان گیت‌هاب موجود در قالب، قالب‌های `child-v`/`parent-v` را بررسی می‌کند؛ در کد افزونهٔ همیار پزشک‌ها به‌روزرسان گیت‌هاب پیدا نشد. افزونه یا اتصال خارجی دیگر روی سایت ممکن است رفتاری متفاوت داشته باشد، اما بررسی نشده است.
- اگر آپدیت خودکار افزونه ظاهر نشد، مدیر می‌تواند فایل ZIP نصبی بالا را از GitHub دانلود کند و در «افزونه‌ها ← افزودن افزونه ← بارگذاری افزونه» با تأیید جایگزینی نسخهٔ فعلی نصب کند؛ این فایل ZIP افزونه است، نه Source code ZIP کل مخزن. پیش از این کار بکاپ فایل و DB و مسیر بازیابی را کنترل کنید و نسخهٔ نصب‌شدهٔ قبلی را برای بازگشت نگه دارید.

## روشن‌کردن feature flag و migration

۱. پیش از تست با دادهٔ ساختگی، بکاپ کامل و امکان بازگردانی فایل‌ها و دیتابیس را کنترل و دسترسی عمومی به روند آزمایشی را محدود کنید. ابتدا افزونه را با flag خاموش به‌روزرسانی و کارکرد قبلی، نسخهٔ افزونه و داشبورد را بررسی کنید. در حالت پیش‌فرض، جدول‌های رزرو جدید ساخته نمی‌شوند و رزرو فعال نیست.

۲. **برای روشن‌کردن کل قابلیت، تنظیمی در پنل وجود ندارد.** در فایل `wp-config.php` وردپرس، قبل از خط پایانی «That's all, stop editing» این خط را قرار دهید؛ اگر همین ثابت قبلاً تعریف شده، تعریف قبلی را بررسی و تغییر دهید، دو بار تعریف نکنید:

```php
define( 'HJ_BOOKING_ENABLED', true );
```

مقدار باید boolean `true` باشد، نه رشتهٔ `'true'`. تغییر `wp-config.php` را فقط مدیر سایت انجام دهد و فایل را برای گفتگو ارسال نکند.

۳. با مدیر دارای `manage_options` به یکی از صفحه‌های پیشخوان بروید. اگر تأیید schema ثبت نشده باشد، در `admin_init` مهاجرت تلاش می‌شود؛ با flag روشن و مدیر دارای مجوز، در فعال‌سازی افزونه هم تلاش می‌شود. به‌روزرسانی با flag خاموش جدول نمی‌سازد. اگر اتصال اختصاصی، مجوز ساخت/خواندن جدول، InnoDB یا schema پشتیبانی نشود، مهاجرت fail-closed است و اخطار «ساختار نوبت‌دهی تأیید نشد» در پیشخوان مدیر نمایش داده می‌شود؛ در این حالت توقف کنید، flag را خاموش کنید و مشکل را بدون دادهٔ شخصی گزارش دهید. CI تازه‌نصب، تکرار و ناسازگاری را در MariaDB دورریختنی بررسی کرده است، نه روی سایت شما. schema بعد از تأیید اولیه در هر درخواست دوباره بررسی نمی‌شود؛ تغییر دستی بعدی schema نیازمند بررسی مجدد است.

۴. **روشن‌کردن flag به‌تنهایی نوبت‌گیری هیچ پزشکی را فعال نمی‌کند.** UI برای روشن‌کردن تنظیم نوبت‌دهی تک‌تک پزشکان در نسخهٔ فعلی وجود ندارد. یک پروفایل و حساب کاملاً ساختگی با عنوان `HJ-TEST-ONLY` بسازید، مطمئن شوید مالک آن همان حساب ساختگی است و پیش از تغییر فیلدهای ساعات موجود از آن‌ها خروجی امن داشته باشید؛ `schedules` تنها منبع رزرو است و ساعات ACF موجود به آن خودکار منتقل نمی‌شوند. برای فعال‌کردن فقط همان پروفایل، اپراتور مورد اعتمادِ دارای WP-CLI می‌تواند از مثال زیر استفاده کند. اگر WP-CLI یا تشخیص مطمئن سایت و حساب آزمایشی در دسترس نیست، تست رزرو مسدود است؛ مستقیم جدول را ویرایش نکنید.

در پوشهٔ وردپرسِ درست، مقدار `HJ_EXPECTED_HOST` را نام میزبان دقیق همین سایت و `HJ_TEST_DOCTOR_ID` را شناسهٔ پروفایل **ساختگی** قرار دهید و شناسهٔ مدیر را به جای `ADMIN_ID` بگذارید. هیچ رمز یا توکنی نیاز نیست. شرط نام پروفایل عمداً مانع تنظیم پروفایل واقعی است:

```sh
wp --user=ADMIN_ID eval '
$host = wp_parse_url(home_url("/"), PHP_URL_HOST);
$expected = getenv("HJ_EXPECTED_HOST");
$id = (int) getenv("HJ_TEST_DOCTOR_ID");
if (!$expected || $host !== $expected || !defined("HJ_BOOKING_ENABLED") || HJ_BOOKING_ENABLED !== true || !current_user_can("manage_options") || !function_exists("hj_booking_ready") || !hj_booking_ready() || get_post_type($id) !== "doctor" || get_post_status($id) !== "publish" || get_the_title($id) !== "HJ-TEST-ONLY") { WP_CLI::error("Guard failed; no change made."); }
$r = hj_booking_configure($id, 30, 5, true);
if (($r["status"] ?? "") !== "configured") { WP_CLI::error("Configuration failed; stop."); }
WP_CLI::success("Synthetic test doctor configured.");
'
```

۵. فقط در حساب ساختگی پزشک، ساعات آزمایشی را در داشبورد ذخیره کنید؛ سپس با دو بیمار ساختگی و یک منشی ساختگی، اسلات، ورود واقعی Google، لغو، دسترسی‌ها، موبایل و کش را طبق موارد قابل‌اعمال [برنامهٔ آزمون](BOOKING-STAGE4-STAGING-PLAN.fa.md) بررسی کنید. از دادهٔ هویتی یا سلامت واقعی در تست، لاگ، تصویر و گفتگو استفاده نکنید. سناریوی قطع ارتباط یا خرابی را بدون ابزار امن روی سایت زنده شبیه‌سازی نکنید.

## توقف و بازگشت

اگر خطای schema، دسترسی متقاطع، نوبت تکراری، افشای داده یا تغییر نامنتظر ساعات مشاهده شد، تست را متوقف و با تغییر مقدار به `false` در `wp-config.php` قابلیت را خاموش کنید. خاموش‌کردن flag جدول‌ها و داده‌ها را حذف یا خطاهای قبلی را اصلاح نمی‌کند. در صورت نیاز، بازگردانی فایل‌ها و DB از بکاپ مطابق روش مدیر انجام می‌شود؛ بازگرداندن DB ممکن است تغییرات پس از زمان بکاپ را از بین ببرد. بستهٔ نسخهٔ فعلیِ نصب‌شده را قبل از جایگزینی حفظ کنید. نتیجهٔ آزمون با نسخه‌ها و مدرک غیرحساس ثبت شود.

سه بدهی فرم و writerهای مستقل ACF همچنان بازند؛ پذیرش ریسک هیچ‌کدام را از نظر فنی حل نمی‌کند. [CI کد migration و رزرو](https://github.com/lakanzino/OR-site/actions/runs/42220741185) و [CI سازگاری](https://github.com/lakanzino/OR-site/actions/runs/42220383990) برای runtime همین بسته سبز بوده‌اند؛ OAuth و ACF واقعی و کارایی محیط مقصد اثبات نشده‌اند.
