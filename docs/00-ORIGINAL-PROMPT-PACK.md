# بسته پرامپت ایجنت — سایت آموزشی اتاق عمل (وردپرس فارسی)

> نحوه استفاده: ابتدا «فاز ۰» را یک‌بار به ایجنت بدهید (قانون ثابت پروژه). سپس هر فاز را جداگانه بدهید. پایان هر فاز، ایجنت گزارش تست را تولید می‌کند و فقط با گزارش سبز وارد فاز بعد می‌شود.

## فاز ۰ — منشور پروژه (یک‌بار، قبل از همه)

```
نقش: تو مهندس ارشد وردپرس (Block Theme / Gutenberg) و معمار سیستم‌های طراحی هستی و تنها ایجنت این پروژه‌ای. همه کارها (معماری، کد، تست، مستندسازی، محتوای نمونه) با توست.

## درباره پروژه
سایت فارسی آموزشی با موضوع «فرایند عمل جراحی از قبل تا بعد»، ساخته‌شده توسط تکنیسین‌های اتاق عمل. هدف: بیمار بداند با چه چیزهایی روبه‌رو می‌شود و با آگاهی، آرامش بیشتری داشته باشد.
محتوا شامل: سوالات رایج قبل از عمل، رفع استرس، کارهای توصیه‌شده قبل از عمل، شرح کلی و قابل‌فهم آنچه حین عمل رخ می‌دهد، مراقبت‌های بعد از عمل، معرفی بخش‌های اتاق عمل، معرفی دستگاه‌ها، و محتوای آموزشی دانشجویان (معرفی ابزار و نحوه کار).
پلتفرم: وردپرس فارسی (fa_IR، RTL). قالب والد اختصاصی + قالب فرزند مخصوص محتوای پیراپزشکی.

## قوانین محتوایی (غیرقابل‌تغییر)
1. سایت هیچ تشخیص، نسخه، دوز دارو یا تحلیل تخصصی پزشکی ارائه نمی‌دهد؛ فقط توضیح فرایند و آمادگی.
2. هرجا متن نمونه (seed) لازم است، فقط متن جای‌نگهدار واضح مثل «[متن نمونه — توسط تیم محتوا جایگزین شود]» بگذار. هرگز ادعای پزشکی، آمار یا توصیه درمانی از خودت نساز.
3. بلاک «سلب مسئولیت پزشکی» و «بازبینی‌شده توسط / تاریخ بروزرسانی» در همه قالب‌های مقاله اجباری است.

## استقلال تو
- برای هیچ تصمیمی منتظر تایید من نمی‌مانی. تصمیم را بر پایه استانداردهای رسمی بگیر: WordPress Coding Standards، مستندات Block Editor، WCAG 2.2 AA، Core Web Vitals، schema.org، و دستورالعمل‌های Google Search.
- هر تصمیم معماری مهم را در `docs/DECISIONS.md` (ADR کوتاه: زمینه، تصمیم، دلیل، جایگزین‌ها) ثبت کن.
- مجاز و تشویق می‌شوی از مخازن عمومی GitHub یاد بگیری (مثل Twenty Twenty-Five، Frost، Ollie و WordPress/gutenberg، wp-env، WPCS). الگوها و معماری را مطالعه کن؛ با رعایت لایسنس، کد را کپی نکن مگر لایسنس سازگار (GPL-2.0+) باشد و منبع را در `docs/CREDITS.md` بنویس.
- از Google Drive (در صورت وجود محتوا/برند/لوگو) به‌عنوان ورودی استفاده کن؛ خروجی‌ها فقط داخل مخزن گیت‌هاب.

## قواعد مهندسی
- Block Theme کامل (theme.json نسخه ۳ یا جدیدتر)، بدون page builder، بدون وابستگی به افزونه‌ی پولی، بدون jQuery در فرانت.
- اولویت: بلاک‌های داینامیک (render.php) تا تغییر ساختار HTML یک بلاک، روی کل سایت اعمال شود بدون Block Validation Error.
- همه چیز RTL-first، موبایل-فرست، ریسپانسیو، قابل‌دسترس (کیبورد، کنتراست، aria)، سبک و بدون CLS.
- کد: کوچک، ماژولار، نام‌گذاری استاندارد (PHP: WPCS و prefix؛ JS/CSS: BEM یا کلاس‌های `wp-block-{ns}-{name}`)، کامنت کوتاه، بدون کد مرده.
- امنیت: escaping/sanitization/nonce/capability در هر نقطه لازم.
- Git: شاخه‌ی هر فاز `phase/N-name`، کامیت‌های Conventional Commits، در پایان فاز PR با گزارش، سپس merge به `main` و تگ `vX.Y.0`.

## پروتکل پایان هر فاز (الزامی)
1. همه‌ی تست‌ها و لینترهای آن فاز را اجرا کن.
2. فایل `docs/reports/phase-N.md` بساز: خلاصه کار، تصمیم‌ها، نتیجه تست‌ها (عدد و وضعیت)، مشکلات باز، ریسک‌ها، پیشنهاد فاز بعد.
3. اگر تستی قرمز بود، خودت رفعش کن و دوباره اجرا کن؛ تا سبز نشده فاز بسته نمی‌شود.
4. در انتها فقط یک خلاصه‌ی کوتاه ۵–۱۰ خطی به من بده.

تایید: فقط بگو «منشور دریافت شد» و منتظر فاز ۱ بمان.
```

## فاز ۱ — زیرساخت مخزن، محیط توسعه و کیفیت کد

```
هدف: اسکلت حرفه‌ای پروژه با ابزارهای کیفیت، قبل از نوشتن هر قالب.

کارها:
1. ساختار مخزن (monorepo):
   - `themes/prm-core/`  → قالب والد (Block Theme)
   - `themes/prm-child-or/` → قالب فرزند پیراپزشکی (اتاق عمل)
   - `plugins/` (خالی؛ فقط اگر ضرورت واقعی بود)
   - `bin/`  → اسکریپت‌های ابزار (WP-CLI و غیره)
   - `docs/`، `tests/`، `.github/workflows/`
   (نام‌ها پیش‌فرض‌اند؛ اگر استاندارد بهتر دیدی عوض کن و در DECISIONS ثبت کن. Text domain و prefix یکتا انتخاب کن.)
2. محیط توسعه: `@wordpress/env` (wp-env) با وردپرس آخرین نسخه‌ی پایدار، زبان fa_IR، پیوند یکتا `/%postname%/`، تنظیم منطقه‌زمانی Asia/Tehran و فعال‌سازی WP_DEBUG.
3. ابزارها: npm با `@wordpress/scripts` (build، lint، test)، Composer با PHPCS + WPCS + PHPCompatibility + PHPUnit، ESLint، Stylelint (با ruleset وردپرس)، EditorConfig، Prettier سازگار.
4. GitHub Actions: lint (PHP/JS/CSS)، build، unit test، و در صورت امکان e2e در هر PR. Dependabot برای وابستگی‌ها.
5. فایل‌های پایه: README (راه‌اندازی در ۵ دستور)، CONTRIBUTING، `.gitignore`، `CODEOWNERS`، قالب PR و Issue.
6. دو قالب خالی اما معتبر: والد با `style.css` header و `theme.json` حداقلی؛ فرزند با `Template: prm-core` و فعال‌شدنی بدون خطا.

تست پایان فاز: `wp-env start` موفق، هر دو قالب فعال‌شدنی، همه‌ی لینترها و CI سبز، build بدون هشدار.
گزارش: docs/reports/phase-1.md
```

## فاز ۲ — سیستم طراحی (Design Tokens) و تنظیمات سراسری

```
هدف: «یک منبع حقیقت» برای ظاهر. تغییر یک توکن، کل سایت را تغییر دهد.

کارها در `prm-core`:
1. `theme.json`:
   - پالت رنگ معنایی (primary, secondary, accent, surface, text, muted, success, warning, danger, info) با کنتراست WCAG AA؛ حالت آرام و آرامش‌بخش مناسب موضوع پزشکی (سردی ملایم، بدون قرمز تهاجمی). رنگ برند را از Drive یا پوشه‌ی برند بخوان؛ اگر نبود، پالت آبی/سبز آرام پیشنهاد و ثبت کن.
   - تایپوگرافی سیال (fluid) با `clamp`، مقیاس اندازه‌ها، فونت فارسی Vazirmatn یا معادل با لایسنس آزاد، **self-hosted**، فرمت woff2، `font-display: swap`، preload فقط برای وزن‌های کلیدی، subset فارسی/لاتین.
   - Spacing scale، radius، shadow، border، عرض محتوا/عرض کامل، breakpointهای استاندارد.
   - تنظیمات ادیتور: غیرفعال کردن رنگ/فونت سفارشی دلخواه کاربر (فقط توکن‌ها)، محدودکردن کنترل‌های بی‌مصرف.
2. Style Variations (حداقل دو: پیش‌فرض + کنتراست بالا) برای نشان‌دادن قدرت توکن‌ها.
3. CSS پایه‌ی بسیار کم: reset سبک، focus-visible واضح، `prefers-reduced-motion`، `scroll-margin` برای لنگرها، ویژگی‌های logical (`margin-inline`, `padding-block`) به‌جای left/right.
4. پشتیبانی کامل RTL و ارقام فارسی در نمایش (تاریخ/عدد)، `lang` و `dir` صحیح.
5. Template Parts: header، footer، مسیر ناوبری (breadcrumb)، جستجو؛ ناوبری موبایل بدون جاوااسکریپت سنگین (از بلاک Navigation هسته).
6. قالب‌های پایه: index، single، page، archive، search، 404 — همه فقط با بلاک‌های هسته و توکن‌ها.

تست پایان فاز: Lighthouse موبایل (Performance ≥ 95، Accessibility ≥ 98، Best Practices ≥ 95، SEO ≥ 95) روی صفحات پایه، axe بدون خطا، بررسی دستی/خودکار RTL و ۳ عرض صفحه (360/768/1280)، اعتبارسنجی theme.json.
گزارش: docs/reports/phase-2.md
```

## فاز ۳ — معماری بلاک‌ها (Atomic) و رجیستری

```
هدف: زیرساخت بلاک‌های کوچک و ترکیب‌پذیر که از ریزترین تکه‌ها به مقاله برسند.

اصل معماری (چهار لایه):
- L1 Atoms: کوچک‌ترین تکه‌ها (تیتر استاندارد بخش، آیکن، برچسب، تصویر قاب‌دار، دکمه، نشان).
- L2 Molecules: ترکیب چند atom (کارت اطلاعات، آیتم مرحله، آیتم پرسش‌وپاسخ، کارت دستگاه، آیتم چک‌لیست).
- L3 Organisms: بخش کامل با تیتر ثابت (تایم‌لاین مراحل، آکاردئون سوالات، شبکه‌ی دستگاه‌ها، گالری تصاویر، جعبه هشدار، چک‌لیست).
- L4 Templates: چیدمان کامل مقاله (فاز ۵).

کارها:
1. ساخت یک کتابخانه‌ی بلاک در `prm-core/blocks/` با `block.json` (apiVersion 3) برای هر بلاک، namespace یکتا (مثلاً `prm/`)، دسته‌بندی‌های اختصاصی در ادیتور (اتم‌ها، مولکول‌ها، بخش‌ها).
2. بلاک‌ها تا حد امکان **داینامیک** (render.php + attributes) باشند؛ استایل با `style.css` هر بلاک که فقط در صورت استفاده در صفحه بارگذاری می‌شود (conditional asset loading).
3. فایل مرکزی `blocks-manifest.json` (تولید خودکار در build): نام، لایه، وابستگی (کدام بلاک‌ها از کدام استفاده می‌کنند)، نسخه، وضعیت (stable/deprecated)، و جایی که دیده می‌شود.
4. سیستم Deprecation استاندارد: بلاک حذف‌شده یا تغییر ساختاری‌یافته، migration/deprecated تعریف شود تا محتوای قدیمی نشکند.
5. بلاک‌های L1 و L2 اولیه + یک L3 نمونه برای اثبات معماری. تمام استایل‌ها فقط از توکن‌های theme.json (CSS variables) بیایند؛ **هیچ رنگ/اندازه‌ی هاردکد** مجاز نیست. هر بلاک `supports` را با دقت (spacing، typography و غیره) فعال کند.
6. ایجاد Block Styles و Block Variations به‌جای کپی بلاک برای حالت‌های مختلف (مثلاً کارت ساده/برجسته).
7. مستندات `docs/BLOCK-ARCHITECTURE.md`: قوانین ساخت بلاک جدید، نام‌گذاری، نحوه‌ی ثبت در manifest، چک‌لیست قبل از merge.

تست پایان فاز: همه‌ی بلاک‌ها در ادیتور ساخته و ذخیره شوند بدون Block Validation Error؛ تست یونیت رندر؛ تست e2e (Playwright) برای درج و ذخیره هر بلاک؛ بررسی اینکه تغییر یک توکن یا یک render.php روی همه‌ی نمونه‌های درج‌شده اعمال می‌شود؛ Lighthouse و axe روی صفحه‌ی دمو بلاک‌ها.
گزارش: docs/reports/phase-3.md
```

## فاز ۴ — کتابخانه‌ی کامل بلاک‌های محتوایی (حوزه‌ی اتاق عمل)

```
هدف: بلاک‌های اختصاصی حوزه‌ی پیراپزشکی، با تیترهای ثابت و قابل‌استفاده‌ی مجدد، در `prm-child-or` (بلاک‌های عمومی‌تر در `prm-core`؛ بلاک‌های مخصوص حوزه در فرزند).

بلاک‌ها (ساختار، نه محتوای پزشکی):
بیمار:
- «سوالات رایج قبل از عمل» (آکاردئون، تیتر ثابت، قابل‌استفاده با Schema FAQ)
- «کارهای پیشنهادی قبل از عمل» (چک‌لیست تعاملی بدون ذخیره‌ی داده‌ی شخصی)
- «رفع استرس و آرامش» (کارت‌های راهکار + جای تمرین نفس‌گیری ساده با متن)
- «در اتاق عمل چه می‌گذرد؟» (تایم‌لاین مراحل کلی، سطح عمومی)
- «مراقبت‌های بعد از عمل» (چک‌لیست + بخش «چه زمانی با پزشک تماس بگیرم» به‌صورت عمومی با ارجاع به پزشک)
- «جعبه نکته / هشدار / اطلاعات» (۳ واریانت)
- «سلب مسئولیت پزشکی»، «بازبینی‌شده توسط»، «تاریخ بروزرسانی»، «زمان مطالعه»، «منابع و مراجع»، «واژه‌نامه‌ی ساده» (tooltip قابل‌دسترس)
معرفی:
- «کارت بخش اتاق عمل» (نام، کاربرد کلی، تصویر)
- «کارت دستگاه» (نام، کاربرد عمومی، تصویر، ایمنی عمومی)
- «شبکه‌ی کارت‌ها» (فیلترپذیر با CSS/JS سبک)
دانشجویان:
- «کارت ابزار جراحی/آموزشی» (نام، کاربرد، نحوه‌ی کار مرحله‌ای، نکات ایمنی)
- «مراحل کار» (Step-by-step)، «جدول مقایسه» (ریسپانسیو)، «کوییز کوتاه» (اختیاری، بدون وابستگی سنگین)
عمومی:
- «گالری تصویر» و «آکاردئون تصویر» (lightbox قابل‌دسترس بدون کتابخانه‌ی سنگین)، «ویدیوی لود تنبل» (facade)، «کارت نویسنده/تیم»، «فراخوان/CTA»، «فهرست مطالب خودکار».

قواعد:
- هر بلاک تیتر پیش‌فرض ثابت دارد (قابل تغییر در ادیتور اما با مقدار پیش‌فرض استاندارد) و در `blocks-manifest.json` ثبت می‌شود.
- هر بلاک از اتم‌ها و مولکول‌های فاز ۳ ساخته شود؛ تکرار کد ممنوع.
- تصاویر: ابعاد ثابت (aspect-ratio)، `srcset`، `loading=lazy` به‌جز تصویر اول، alt اجباری با هشدار در ادیتور.
- متن‌های نمونه فقط جای‌نگهدار باشند (قانون فاز ۰).

تست پایان فاز: درج همه‌ی بلاک‌ها در یک صفحه‌ی «کاتالوگ بلاک» (فقط محیط توسعه، noindex)، بدون خطای ولیدیشن/کنسول؛ axe و Lighthouse؛ تست ریسپانسیو ۳ عرض؛ سنجش وزن CSS/JS هر صفحه (بودجه: JS فرانت‌اند کل صفحه ≤ 30KB gzip در حالت عادی).
گزارش: docs/reports/phase-4.md
```

## فاز ۵ — قالب‌های مقاله، الگوها (Patterns) و ساختار محتوا

```
هدف: تبدیل بلاک‌ها به مقاله با چند کلیک، با چیدمان استاندارد برای هر موضوع.

کارها:
1. ساختار محتوا:
   - پست تایپ‌ها (فقط اگر لازم): `or_device` (دستگاه)، `or_section` (بخش اتاق عمل)، `or_instrument` (ابزار – آموزشی). مقالات عمومی روی `post`. همه با REST فعال و پشتیبانی ادیتور بلاک.
   - تاکسونومی‌ها: «مرحله» (قبل از عمل / حین عمل / بعد از عمل)، «مخاطب» (بیمار / دانشجو)، «موضوع».
   - فیلدها: ترجیحاً meta ثبت‌شده با `register_post_meta` و `show_in_rest`؛ بدون وابستگی به ACF.
2. Block Patterns (در پوشه‌ی `patterns/`، ثبت خودکار، دسته‌بندی «قالب مقاله» و «بخش‌ها») و **Template Lock** (`contentOnly` یا `templateLock`) برای ثابت ماندن ساختار و تیترها؛ نویسنده فقط محتوا را پر کند.
3. قالب‌های مقاله (هر کدام یک Pattern کامل + Template اختصاصی نوع پست):
   - راهنمای بیمار (قبل از عمل)
   - رفع استرس و آمادگی ذهنی
   - توضیح فرایند «در اتاق عمل چه می‌گذرد؟»
   - مراقبت بعد از عمل
   - پروفایل بخش اتاق عمل
   - پروفایل دستگاه
   - درس دانشجویی (معرفی ابزار و نحوه‌ی کار)
   - صفحه‌ی سوالات متداول
   - صفحه‌ی آرشیو هر مرحله، صفحه‌ی اصلی، درباره‌ی ما، تماس
4. **Synced Patterns** (بلاک‌های مشترک مثل سلب مسئولیت، CTA، کارت تیم) برای تغییر یک‌جا و اعمال روی کل سایت. تفاوت را در مستندات روشن کن: «تغییر ظاهر → توکن/استایل بلاک»، «تغییر ساختار → render.php»، «تغییر محتوای مشترک → Synced Pattern».
5. صفحه‌ی اصلی و آرشیوها با Query Loop و Pattern؛ breadcrumb، مقالات مرتبط (بر اساس تاکسونومی)، قبلی/بعدی.
6. محتوای دمو: برای هر قالب یک نمونه‌ی کامل با متن جای‌نگهدار (seed با WP-CLI در `bin/seed-demo.sh`، قابل‌اجرای مجدد و حذف).

تست پایان فاز: ساخت یک مقاله از هر قالب با WP-CLI/e2e، تایید قفل‌بودن تیترها، رندر درست در همه‌ی عرض‌ها؛ axe/Lighthouse روی هر قالب؛ تست اینکه ویرایش یک Synced Pattern روی همه‌ی صفحات اعمال می‌شود.
گزارش: docs/reports/phase-5.md
```

## فاز ۶ — ابزارهای مدیریت بلاک (حذف/جایگزینی سراسری)

```
هدف: ایجنت (یا من) بتواند یک بلاک را در کل سایت پیدا، جایگزین یا حذف کند، بدون خراب‌شدن محتوا.

کارها:
1. دستورات WP-CLI در `bin/` یا یک mu-plugin سبک با namespace `prm`:
   - `wp prm block usage <block-name>`: فهرست تمام پست‌های استفاده‌کننده (شامل Synced Patternها، قالب‌ها و Template Partها) با شمارش.
   - `wp prm block remove <block-name> [--dry-run] [--post-type=...]`: حذف امن همه‌ی نمونه‌ها (parse با `parse_blocks`/`serialize_blocks`، نه regex). پیش از اجرا بکاپ JSON از post_content و گزارش تغییر. پیش‌فرض `--dry-run`.
   - `wp prm block replace <old> <new> [--map-attrs=...]`: جایگزینی با نگاشت attribute.
   - `wp prm block audit`: یافتن بلاک‌های Deprecated، یتیم (بدون استفاده)، و بلاک‌هایی که ولیدیشن ندارند.
   - `wp prm manifest check`: تطابق `blocks-manifest.json` با بلاک‌های واقعی ثبت‌شده.
2. حذف خود بلاک از کد: چک‌لیست استاندارد (deprecated مرحله‌ای → migrate → حذف) در `docs/BLOCK-LIFECYCLE.md`.
3. اسکریپت `bin/create-block` برای ساخت اسکلت بلاک جدید با همه‌ی استانداردهای فاز ۳ (ثبت manifest، تست، مستندات).
4. دستورالعمل کوتاه «برای ایجنت» در `docs/AGENT-PLAYBOOK.md`: چگونه یک بلاک اضافه/حذف/تغییر دهد، چه تست‌هایی بزند، و در هر حالت کدام ابزار را استفاده کند.

تست پایان فاز: تست یونیت/یکپارچه روی دیتابیس دمو؛ اجرای remove در حالت dry-run و واقعی و سپس بازگردانی از بکاپ؛ تضمین اینکه حذف یک بلاک، ساختار بقیه‌ی محتوا را نمی‌شکند؛ گزارش پوشش تست.
گزارش: docs/reports/phase-6.md
```

## فاز ۷ — سئو، اسکیما، عملکرد، دسترسی‌پذیری و امنیت

```
هدف: استاندارد جهانی و گوگل، بدون افزونه‌ی سنگین.

کارها:
1. سئوی فنی: ساختار تیترهای صحیح (یک H1)، Open Graph/Twitter، canonical، robots، sitemap هسته‌ی وردپرس، breadcrumb با Schema. اگر افزونه‌ی سئو (Rank Math/Yoast) فعال بود، خروجی تکراری نده (تشخیص و غیرفعال‌سازی خودکار بخش مشابه).
2. Schema.org (JSON-LD) داینامیک و صحیح: `Article`/`MedicalWebPage` (با `lastReviewed` و `reviewedBy` از بلاک‌ها)، `FAQPage` (از بلاک پرسش‌وپاسخ)، `BreadcrumbList`، `Organization`/`WebSite` با SearchAction. فقط داده‌ای که واقعاً در صفحه هست.
3. عملکرد: بودجه‌ی Core Web Vitals (LCP < 2.5s، INP < 200ms، CLS < 0.1 روی موبایل)، حذف CSS/JS غیرضروری (فقط بلاک‌های استفاده‌شده)، preload فونت، تصاویر WebP/AVIF با fallback، `fetchpriority` برای LCP، حذف emoji/embeds اضافی، کش‌پذیری مناسب، headerهای امنیتی پیشنهادی در مستندات.
4. دسترسی‌پذیری: WCAG 2.2 AA کامل، لینک «رفتن به محتوا»، ناوبری کیبورد، فوکوس مرئی، کنتراست، aria صحیح، اندازه‌ی هدف لمسی، حالت کاهش حرکت.
5. امنیت و حریم خصوصی: بدون ردیاب شخص‌ثالث، بدون ذخیره‌ی داده‌ی سلامت کاربران، escaping کامل، بررسی با PHPCS Security rules، پیشنهاد تنظیمات سخت‌سازی وردپرس و فهرست افزونه‌های توصیه‌شده/ممنوع در `docs/PLUGINS.md` (حداقل ممکن).
6. فارسی: slug ها، جستجوی فارسی (نرمال‌سازی ی/ک و ارقام)، تاریخ شمسی به‌صورت اختیاری و بدون ایجاد ناسازگاری در schema (schema همیشه ISO میلادی).
7. صفحات حقوقی: قالب «حریم خصوصی»، «شرایط استفاده»، «سلب مسئولیت پزشکی» با متن جای‌نگهدار.

تست پایان فاز: Lighthouse CI (مثل فاز ۲ روی همه‌ی قالب‌ها)، Rich Results Test/validator برای schema، axe روی همه‌ی قالب‌ها، تست حذف ردپای افزونه‌ی سئو، اسکن امنیتی کد، گزارش وزن صفحه.
گزارش: docs/reports/phase-7.md
```

## فاز ۸ — تست جامع، مستندات و تحویل

```
هدف: کیفیت نهایی و قابلیت ارتقای بلندمدت.

کارها:
1. مجموعه‌ی تست کامل در CI: PHPUnit، Playwright (مسیرهای کلیدی + همه‌ی قالب‌های مقاله)، visual regression در RTL و ۳ عرض، Lighthouse CI، axe، تست مهاجرت/دپریکیشن بلاک‌ها.
2. تست سازگاری: آخرین نسخه‌ی وردپرس و نسخه‌ی قبلی، PHP 8.1+ ، مرورگرهای اصلی، افزونه‌های رایج (کش، سئو، فرم تماس).
3. مستندات کامل:
   - README و راهنمای نصب (روی هاست معمولی ایران هم)
   - `docs/CONTENT-GUIDE.md` برای تیم تکنیسین‌ها: چگونه با Pattern مقاله بسازیم (غیرفنی، مرحله‌به‌مرحله، با تصویر)
   - `docs/BLOCK-CATALOG.md` خودکار از manifest (تصویر، کاربرد، تیتر ثابت)
   - `docs/UPGRADE.md`، `docs/BLOCK-LIFECYCLE.md`، `docs/AGENT-PLAYBOOK.md`
   - CHANGELOG (Keep a Changelog) و نسخه‌گذاری معنایی
4. بسته‌بندی: اسکریپت ساخت ZIP قالب‌ها (والد و فرزند)، بدون فایل توسعه، به‌علاوه‌ی Release در GitHub با تگ و فایل‌ها.
5. چک‌لیست انتشار (go-live): بکاپ، HTTPS، کش، robots، sitemap، آنالیتیکس بدون ردیابی شخصی (اختیاری)، مانیتورینگ.
6. بازبینی نهایی: ممیزی خودت از کل مخزن (کد مرده، تکرار، بلاک‌های بلااستفاده، ناسازگاری manifest، هشدارهای کنسول) و رفع آن‌ها.

تست پایان فاز: همه‌ی چک‌ها سبک سبز؛ نصب تازه از ZIP روی وردپرس تمیز، فعال‌سازی، import دمو، و عبور از تست‌های e2e.
گزارش نهایی: docs/reports/phase-8.md + فهرست «کارهای بعدی پیشنهادی»
```
