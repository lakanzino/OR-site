# معماری ربات معاینه بیمار لکس — آن‌چنان‌که ساخته شده

**نسخهٔ سند:** `lax-robot-0.1.0` · ۳۱ اکتبر ۲۰۲۶

این سند معماری **واقعی** را توصیف می‌کند: نام فایل‌ها، قراردادها و مرزهایی که امروز در مخزن هستند. هر جا چیزی هنوز ساخته نشده، با «نیست» علامت خورده است.

---

## ۱. شکل کلی

```text
                     ┌──────────────────────────────────────────┐
                     │  بستهٔ دانش (داده، JSON)                  │
                     │  docs/symptom-checker/phase-1/            │
                     │   v1: knowledge-bundle.v1.json            │
                     │   v2: knowledge-bundle.v2.json (ساخته‌شده) │
                     └───────────────┬──────────────────────────┘
                                     │ همان فایل، دو شکل
                     ┌───────────────▼──────────────────────────┐
                     │  موتور  symptom-checker/engine/src/       │
                     │  load-bundle → adapter → validate →       │
                     │  strategy → engine → evidence             │
                     └───────────────┬──────────────────────────┘
                                     │ result() — یک شکل ثابت
                     ┌───────────────▼──────────────────────────┐
                     │  رابط  symptom-checker/ui/                │
                     │  app.js + view-model.js + question-help   │
                     └───────────────┬──────────────────────────┘
                                     │ فقط در مرورگر کاربر
        ┌────────────────────────────▼───────────────────────────┐
        │  افزونهٔ وردپرس  plugins/hamyar-symptom-checker/         │
        │  برگهٔ پیش‌نویس اختصاصی، بارگذاری دارایی محلی            │
        └────────────────────────────────────────────────────────┘
```

هیچ پیکانی از رابط به بیرون نمی‌رود: پاسخ‌ها در حافظهٔ صفحه می‌مانند و صفحه هیچ درخواستی جز دو فایل محلی (بسته و نقشهٔ شواهد) نمی‌فرستد. `privacy_scan.py` همین را می‌سنجد.

## ۲. سه شکل داده و یک آداپتر

| شکل | کجاست | برای چه |
| --- | --- | --- |
| `1.0.0` (v1) | `knowledge-bundle.v1.json` + `evidence-map.v1.json` | شکل منتشرشده؛ **قفل طلایی** روی آن است |
| `2.0.0` (v2) پایه | `knowledge-bundle.v2.base.json` | خروجی مبدل از v1؛ ثابت |
| `2.0.0` (v2) نهایی | `knowledge-bundle.v2.json` | پایه + داده‌های نویسندگان؛ همان چیزی که منتشر می‌شود |

`engine/src/adapter.js` **تنها** جایی است که تفاوت دو شکل را می‌داند. بقیهٔ موتور فقط یک مدل داخلی می‌بیند. نگاشت شناسه‌ها از خود داده می‌آید (`legacy_id`)، نه از کد.

قرارداد v2 که در فاز ۳ تثبیت شد: هر بیماری `profile_ref` دارد که **باید** به یک شناسهٔ پروفایل اشاره کند (`…#<id>`). اگر پروفایل بیماری در خود بسته باشد، اشاره به خود بسته است (`symptom-checker.abdomen.v1#chole`) و `link_status: unmapped` می‌گوید هیچ مقاله‌ای وصل نیست.

## ۳. قرارداد موتور

- **پرسش بی‌پاسخ، «نه» نیست.** فقط پاسخ‌های داده‌شده شاهد می‌سازند.
- **«نمی‌دانم» هیچ چیزی را برآورده نمی‌کند** — نه شاهد مثبت است، نه منفی.
- **شاخه‌ها موازی‌اند:** باز شدن یک مسیر هیچ مسیر دیگر را نمی‌بندد.
- **قواعد ایمنی مستقل‌اند** از کارت‌ها؛ ممکن است کارتی نباشد ولی هشدار باشد.
- **`out_of_scope`** پرسش را متوقف و همهٔ کارت‌ها را خاموش می‌کند (بارداری و مانند آن).
- **`result()` فقط فیلد اضافه می‌گیرد**، هرگز فیلدی حذف یا معنایش عوض نمی‌شود. `profile_match` (گروه کیفی `strong/partial/weak`) پیش‌فرض **خاموش** است و فقط با درخواست صریح هاست می‌آید؛ هیچ عددی حمل نمی‌کند.
- **ترتیب پرسش، تزریق‌پذیر:** `strategy.js` واسط `selectNextQuestion(state)` دارد. پیش‌فرض `static_order` و **دقیقاً رفتار قبلی**؛ `adaptive` امروز فقط اسکلت است و آزمون صریحاً می‌گوید باید عیناً مثل `static_order` باشد تا فاز ۴.
- **نگهبان استراتژی داخل موتور است:** استراتژی ترتیب می‌دهد، نه دسترسی؛ پرسش پنهان/تکراری/ناموجود = `QUESTION_STRATEGY_INVALID`.

## ۴. مسئولیت‌ها (و چیزهایی که عمداً نیست)

| لایه | هست | نیست |
| --- | --- | --- |
| موتور | منطق خالص، شاهد، ایمنی، پوشش | شبکه، DOM، ذخیره‌سازی، تصادف، درصد |
| رابط | نمایش کارت/هشدار/پوشش، انتخاب پاسخ، راهنما | ذخیره، ارسال، تصمیم، رتبه‌بندی |
| افزونه | برگه، بارگذاری دارایی، فیلتر کانفیگ | تصمیم‌گیری، آمار، لاگ پاسخ |
| بستهٔ دانش | نشانه، پرسش، بیماری، منبع، متن | عدد احتمال، امتیاز، وزن |
| ابزار نویسندگی | ساخت و سنجش بسته | اجرای موتور روی پاسخ واقعی |

**متن آزاد «نمی‌دانم»** جایی در منطق ندارد: فقط ثبت و نمایش می‌شود تا آدم بخواند؛ روی مسیر، شاهد یا نتیجه اثر صفر دارد.

## ۵. جریان کار نویسنده

```text
v1 ──(v1_to_v2.py)──▶ v2.base.json ──(author.py build-bundle + authoring/)──▶ v2.json
                            ▲                                                  │
                            │                    validate / overlap / report  │
                            └────────────── سه سد: پایتون، قواعد، موتور ◀─────┘
```

- `author.py validate` = schema + ارجاع + پوشش + متن راهنما + **موتور واقعی**.
- `overlap` = جفت‌های هم‌پوشان و جداکنندهٔ قابل‌پرسش؛ بدون جداکننده ⇒ ایست با «به پرسش تازه نیاز دارد».
- `gen-scenarios` = یک شخصیت `typical` برای هر بیماری؛ شخصیت حق ندارد قاعدهٔ پوشش را بی‌خبر فعال کند.
- `build-bundle` = تنها راه ساخت بستهٔ تحویل‌شدنی؛ محتوا عوض شود، نسخهٔ minor بالا می‌رود.

## ۷. چیزهایی که امروز **نیست**

- انتخاب پرسش تطبیقی (فاز ۴) — `adaptive` اسکلت است.
- استفاده از `level` پروفایل در نتیجه — تا فاز ۴ بی‌اثر است و آزمون همین را قفل کرده.
- نمایش `profile_match` در رابط — تا فاز ۶، و فقط با تصمیم صاحب سایت.
- اتصال مقاله به بیماری تازه — `link_status: unmapped` و بدون حدس.
- انتشار عمومی: برگه پیش‌نویس و `noindex` است؛ انتشار تصمیم جداگانه دارد.
