## ۲. `loadBundle()` — یک مدل، دو شکل

پیش‌تر منطق تشخیص v1/v2 داخل `createSession` بود. الان یک لایهٔ مستقل است:

```js
const { format, schemaVersion, bundle, evidenceMap, bundleId, bundleVersion } = loadBundle(raw, { evidenceMap });
```

- `format` شکلِ ورودی است (`1.0.0` یا `2.0.0`) و `bundle` همیشه همان مدل داخلی v1 — پس بقیهٔ موتور حتی نمی‌داند بستهٔ دوم وجود دارد.
- ورودی غیرشیء → `BUNDLE_FORMAT_INVALID` با نام آنچه گرفته شد؛ نسخهٔ ناشناس → `BUNDLE_VERSION_UNSUPPORTED` با همان نسخه در پیام؛ بستهٔ ناقص → `BUNDLE_INVALID` همراه فهرست ایرادها.
- `session.bundleFormat` و `session.schemaVersion` حالا هر دو از لایهٔ بارگذاری می‌آیند.

## ۳. استراتژی — تزریق‌پذیر، ولی امروز همان رفتار

```js
createSession(bundle, { questionStrategy: 'static_order' })      // پیش‌فرض
createSession(bundle, { selectNextQuestion: (state) => ... })    // تابع دلخواه
```

- **`state`** شامل کپی پاسخ‌ها، وضعیت مشتق‌شده، فهرست پرسش‌های مجاز (به ترتیب `ask_order`) و `nextInOrder()` است. کپی است، پس استراتژی نمی‌تواند نشست را دستکاری کند (آزمون دارد).
- **نگهبان:** اگر استراتژی پرسشی برگرداند که وجود ندارد، پنهان است یا قبلاً پاسخ داده شده، موتور `QUESTION_STRATEGY_INVALID` می‌دهد؛ استراتژی ترتیب می‌دهد، نه دسترسی.
- **`adaptive` صادقانه اسکلت است:** بدنهٔ آن امروز `nextInOrder()` است و آزمون صریحاً می‌گوید تا فاز ۴ باید دقیقاً مثل `static_order` باشد. هیچ ادعای تطبیقی‌شدن نمی‌کنیم.
- **پرچم در کانفیگ، نه در UI:** `hjsc_question_strategy` با پیش‌فرض `static_order`؛ هر مقدار ناشناس بی‌صدا به `static_order` برمی‌گردد، چون یک اشتباه تایپی در فیلتر نباید پرسش‌نامه را بی‌پرسش بگذارد. صفحه هیچ کنترلی برای این پرچم ندارد و پاسخ کاربر هم هیچ اثری بر آن ندارد.

## ۴. `profile_match` — سه کلمه، بدون هیچ عددی

`result().profile_match` یک نگاشت `{ conditionId: 'strong' | 'partial' | 'weak' }` است و **فقط وقتی** هاست با `profileMatch: true` درخواستش کند ظاهر می‌شود؛ پیش‌فرض خاموش است، پس شکل `result()` امروز بایت‌به‌بایت همان قبلی می‌ماند.

- مبنا فقط ردیف‌های `level: typical` همان بیماری است؛ `possible` و `rare` و `not_expected` در شمارش نمی‌آیند.
- «گزارش‌شده» یعنی آن نشانه در گروه `present` شواهد آمده باشد. نشانه‌ای که پرسش‌نامه از آن نمی‌پرسد، در مخرجِ *تطبیق* نمی‌آید و به‌عنوان «رد شده» حساب نمی‌شود.
- مرزها در کد ثابت‌اند و هرگز بیرون نمی‌روند؛ خروجی فقط یکی از سه کلمه است. هیچ درصد، امتیاز یا رتبه‌ای ساخته نمی‌شود.
- برای بیماری‌ای که کارتی ندارد، کلید هم ساخته نمی‌شود (نه اینکه `weak` ثبت شود).
- **در UI نمایش داده نمی‌شود** تا فاز ۶؛ امروز هیچ‌جای رابط آن را نمی‌خواند.

## ۷. ریسک‌ها و چیزهایی که عمداً انجام نشد

1. **`adaptive` هنوز هیچ چیزی را تطبیق نمی‌دهد.** اگر امروز کسی با فیلتر آن را روشن کند، رفتار عوض نمی‌شود — و این درست است، چون پیاده‌سازی‌اش فاز ۴ است.
2. **`profile_match` مرزهای عددی دارد (۰.۷ و ۰.۴)** که در خروجی دیده نمی‌شوند. اگر تیم بالینی بعداً بخواهد گروه‌بندی دیگری داشته باشد، تغییرش یک خط است ولی باید در گزارش فاز ۴ ثبت شود.
3. **`profile_match` روی بستهٔ v1 هم کار می‌کند** (چون هر لینک بدون سطح، `typical` حساب می‌شود). این عمدی است تا سایت فعلی هم بتواند از آن استفاده کند.
4. **رابط هنوز آن را نشان نمی‌دهد**؛ اگر کسی از `result()` بخواند، باید بداند فیلد اختیاری است.
5. **اجرای شبانهٔ CI** (هم‌ارزی تفاضلی) از فاز ۱ برقرار است، ولی اولین شبانه هنوز دیده نشده.
