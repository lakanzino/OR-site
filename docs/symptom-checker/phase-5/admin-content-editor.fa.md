# فاز ۵-ب — ویرایش محتوا در پیشخوان وردپرس

تاریخ: ۳۱ اکتبر ۲۰۲۶ · افزونه: **۰.۱.۹** · فاز: ۵-ب رانبوک v2

تصمیم صاحب سایت در همین روز: «ویرایش محتوا در پیشخوان رو کامل کن.» پیش از این، فاز ۵-ب در رانبوک «فقط با تأیید صاحب سایت» علامت خورده بود؛ با این پیام، مجاز شد.

## ۱. چه ساخته شد

یک صفحهٔ مدیریتی: **پیشخوان ← دستیار نشانه‌ها** (`admin.php?page=hj-sc-content`).

| بخش | چه می‌کند |
| --- | --- |
| وضعیت فعلی | می‌گوید صفحه از کدام بسته سرو می‌شود (فایل بارگذاری‌شده یا داخل زیپ)، با نسخه، schema، هش ۸ رقمی، مسیر پوشه و شمار بیماری/پرسش/نشانه/گزینه |
| فهرست فایل‌ها | همهٔ `knowledge-bundle.*.json` معتبر در `uploads/hj-sc/` با نسخه، هش، اندازه؛ دکمهٔ «فعال کن» و برچسب «در حال سرو» |
| بازگشت به خودکار | یک دکمه؛ option را پاک می‌کند و انتخاب «تازه‌ترین فایل معتبر» برمی‌گردد |
| ویرایش متن | برای فایلی که انتخاب می‌کنید: متن پرسش، توضیح «چرا می‌پرسیم»، برچسب گزینه، نام بیماری، پیام قاعدهٔ ایمنی/پوشش، سه متن سلب مسئولیت |
| ذخیره | فایل **تازه** با نسخهٔ بعدی و نام قرارداد می‌سازد و فعالش می‌کند؛ فایل قبلی هرگز بازنویسی یا حذف نمی‌شود |
| بارگذاری | فایل `.json` ساخته‌شده با `author.py publish-bundle` را می‌گیرد، شکلش را می‌سنجد، با نام قرارداد ذخیره و فعال می‌کند |

هیچ صفحه یا برگهٔ عمومی تازه‌ای اضافه نشد؛ نمایش و رفتار صفحهٔ بیمار بایت‌به‌بایت همان است مگر اینکه مدیر محتوا را عوض کند.

## ۲. چه چیزی عمداً قابل ویرایش نیست

فقط **متن** قابل ویرایش است. این‌ها کپی می‌شوند و از فرم قابل تغییر نیستند:

- شناسه‌ها (`question.id`، `option.id`، `condition.id`، شناسهٔ قاعده‌ها)؛
- `evidence` هر گزینه، `state`ها و نگاشت پاسخ→نشانه؛
- `when` قاعده‌های ایمنی و پوشش، `severity`، `result`؛
- ردیف‌های `profile` و `level` هر نشانه؛
- `source_refs` و `link_status`؛
- ترتیب پرسش‌ها (`ask_order`) و شرط نمایش (`visibility`).

دلیلش دو چیز است: (۱) قانون پروژه «با هر تغییر، `result()` فقط فیلد بگیرد و رفتار عوض نشود»؛ (۲) هر تغییری در شاهد یا قاعده، تغییر رفتار بالینی است و باید از مسیر CLI با آزمون طلایی و هم‌ارزی بگذرد، نه از یک کادر متنی.

## ۳. چرا پست‌تایپ ساخته نشد

رانبوک برای فاز ۵-ب `hj_sc_condition` با وضعیت‌های «پیش‌نویس/بازبینی‌شده/منتشرشده» و «تولید بسته فقط با همان ولیداتور CLI» می‌خواست. هر دو شرط با هم در این هاست جمع نمی‌شوند:

- اجرای Node از PHP روی هاست اشتراکی (بدون `exec`، حافظهٔ ۴۰ مگابایت) عملی و امن نیست؛
- نوشتن ولیداتور دوم در PHP، قاعدهٔ «ولیداتور دوم ممنوع» را می‌شکند؛
- پست‌تایپ بدون آن ولیداتور، فقط یک ویرایشگر JSON با ظاهر وردپرس است، نه یک تضمین تازه.

پس مسیر انتخاب‌شده این است: **افزونه فقط «شکل» بسته را می‌سنجد و محتوا را کپی می‌کند**؛ تولید و داوری محتوا همچنان کار `author.py` و تیم است. اگر بعداً یک دروازهٔ «پیش‌نمایش/بازبینی» خواستید، باید به‌عنوان تصمیم جدا (و با پیش‌نمایش سمت مرورگر) طراحی شود؛ این سند آن را رد نمی‌کند، فقط امروز انجامش نمی‌دهد.

## ۴. مدل تهدید و کنترل‌ها

| ریسک | کنترل | آزمون |
| --- | --- | --- |
| کاربر بی‌مجوز وارد شود | `current_user_can( hjsc_admin_capability() )` و `wp_die(403)` در رندر | سناریوی `admin-save-guard`؛ در وردپرس واقعی: کاربر subscriber نمی‌تواند |
| درخواست جعلی (CSRF) | `check_admin_referer` روی هر سه عمل (ذخیره/فعال‌سازی/بارگذاری) | بدون nonce → `bad_nonce` و هیچ فایلی نوشته نمی‌شود |
| نوشتن بیرون از پوشه | `sanitize_file_name` + `basename` + الگوی نام قرارداد | `../../wp-config.php` رد می‌شود |
| آپلود فایل اجرایی | فقط پسوند `.json`، محتوا باید JSON با schema 2.0.0 باشد | `evil.php` رد می‌شود و در پوشهٔ بارگذاری فایل اجرایی نیست |
| `tmp_name` جعلی در درخواست وب | `is_uploaded_file()` وقتی `REQUEST_METHOD` هست | سناریوی «forged tmp_name» |
| XSS از متن بسته | `esc_html`/`esc_attr`/`esc_textarea` در همهٔ خروجی‌ها | متن `<script>` به‌صورت escape‌شده دیده می‌شود |
| دستکاری ساختار از فرم | فیلدها از خود بسته ساخته می‌شوند؛ کلید تازه/ساختاری نادیده گرفته می‌شود | ارسال `schema_version`، `evidence`، پرسش تازه → `unchanged` |
| حذف محتوا | هیچ عمل حذف/بازنویسی وجود ندارد؛ نام فایل شامل هش است | پس از ذخیره، دو فایل روی دیسک و بایت فایل قبلی یکسان |
| ذخیره یا ارسال پاسخ بیمار | این صفحه فقط فایل محتوا را می‌خواند/می‌نویسد | `privacy_scan.py` و بازرسی درخواست‌های صفحهٔ عمومی |

## ۵. آزمون‌ها

| دروازه | نتیجه |
| --- | --- |
| PHP واقعی (WASM، روی زیپ ساخته‌شده) | **۳۱/۳۱ سناریو، ۲۱۳ بررسی** — ۷ سناریوی تازهٔ `admin-*` |
| WordPress واقعی (Playground ۶.۸.۳) | **۸۵/۸۵ بررسی** — منو ثبت می‌شود، مالک صفحه را می‌بیند، subscriber نمی‌بیند، ذخیره فایل `knowledge-bundle.0.2.1-draft.<هش>.json` می‌سازد، صفحهٔ بیمار همان را با `ver=<هش>` سرو می‌کند، متن ویرایش‌شده در بستهٔ سروشده هست، فایل داخل زیپ دست‌نخورده می‌ماند و `wp-admin` برای بازدیدکننده ۳۰۲ می‌دهد |
| حریم خصوصی | `privacy_scan.py` پاک · نه ذخیره، نه ردیابی، نه مقصد شبکه‌ای ناشناس |
| موتور/رابط | ۱۲۹/۱۲۹ · هم‌ارزی v1↔v2 صفر اختلاف · عکس طلایی بدون تغییر |
| بسته | `build_package.py --check` سبز (۲۴ فایل) |

## ۶. چه چیزی اثبات نشده

- روی سایت زنده نصب و آزمایش نشده؛ کش LiteSpeed با `ver=` در محیط واقعی آزموده نشده.
- ویرایش از پیشخوان **بی‌درنگ منتشر می‌شود** (مثل فاز ۵-الف)؛ هیچ دروازهٔ «بازبینی تیمی» میان ذخیره و انتشار نیست. `review_status: pending_team_review` فقط مهر است، نه توقف.
- اگر مدیر متنی را عوض کند که در UI استفاده نمی‌شود (مثلاً پیام قاعده‌ای که هرگز فعال نمی‌شود)، همان متن بی‌اثر می‌ماند؛ ابزار این را هشدار نمی‌دهد.
- حالت‌های چند کاربر هم‌زمان (دو مدیر که هم‌زمان ذخیره می‌کنند) آزموده نشده؛ نام فایل با هش محتوا ساخته می‌شود، پس هر دو نسخه سالم می‌مانند، ولی «آخرین ذخیره» برندهٔ فعال‌سازی است.

## ۷. کارهای باز

1. نصب ۰.۱.۹ روی سایت واقعی و یک ویرایش واقعی متن + بازگشت (تصمیم صاحب سایت).
2. تصمیم دربارهٔ دروازهٔ «پیش‌نمایش/بازبینی» پیش از انتشار خودکار — اگر لازم است، طرح جدا.
3. اگر ویرایش ساختاری (نشانه/قاعده/بیماری) در پیشخوان لازم شد، مسیرش همان `author.py` + بارگذاری فایل است، نه فرم تازه.
