## ۲) مدل داده

### ۲.۱ بستهٔ دانش — شمارش فعلی

| بخش | تعداد | نقش |
|---|---|---|
| `symptoms` | ۲۷ | نشانه‌های استاندارد (مثل `s_pain_rlq` = درد پایین راست شکم) |
| `questions` | ۱۷ | پرسش‌ها با `ask_order`، نوع، گزینه‌ها و قاعدهٔ نمایش |
| `conditions` | ۵ | موضوع‌ها؛ هرکدام ۶ تا ۱۳ نشانه و یک `article_slug` |
| `paths` | ۶ | قواعدی که یک موضوع را «باز» می‌کنند |
| `safety_rules` | ۸ | هشدارهای فوری/توصیه‌ای، مستقل از نتیجه |
| `coverage_rules` | ۵ | تصمیم «آیا کارت نشان بدهیم؟» |
| `sources` | ۱۰ | ۵ شناسنامهٔ داخلی + ۵ منبع بالینی بیرونی |

### ۲.۲ یک پرسش

```json
{
  "id": "q_pain_location",
  "ask_order": 20,
  "type": "single",
  "text_fa": "درد را بیشتر کجا حس می‌کنی؟",
  "why_fa": "…",
  "source_refs": ["src_nhs_app", "src_niddk_stone"],
  "visibility": { "any_of": [{ "question_id": "q_pain_present", "answers": ["yes", "unknown"] }] },
  "options": [{ "id": "right_lower", "label_fa": "…" }, …]
}
```

چهار نوع پرسش وجود دارد: `boolean3` (فقط بله/خیر/نمی‌دانم)، `single`، `multi` (با گزینهٔ انحصاری `none`/`unknown`)، و `scale` (۰ تا ۱۰ یا «نمی‌دانم»).

`visibility` فقط دو شکل دارد: `{ "always": true }` یا `{ "any_of": [ … ] }` — یعنی «این پرسش وقتی نشان داده می‌شود که پاسخ فلان پرسش قبلی یکی از این‌ها باشد». موتور اجازه نمی‌دهد پرسشی به پرسش **بعدی** وابسته باشد؛ قاعده در زمان اعتبارسنجی رد می‌شود.

### ۲.۳ یک موضوع و مسیرش

```json
// conditions[]
{ "id": "app", "name_fa": "آپاندیسیت", "article_slug": "appendicitis",
  "profile_ref": "disease-profiles.json#app",
  "link_status": "needs_live_verification",
  "symptom_links": [
    { "symptom_id": "s_pain_migrates_rlq",
      "profile_line": "سپس به پایین سمت راست شکم می‌رود",
      "source_refs": ["src_profile_app", "src_nhs_app"] }, … ],       // ۱۳ مورد
  "red_flag_refs": ["sf_severe_pain", …], "review_status": "pending_team_review" }

// paths[]
{ "id": "p_app_rlq", "condition_id": "app",
  "when": [{ "any_of": [
      { "question_id": "q_pain_location", "answers": ["right_lower"] },
      { "question_id": "q_pain_migrated_rlq", "answers": ["yes"] } ] }],
  "note_fa": "درد پایین راست یا حرکت درد به آن ناحیه…",
  "source_refs": ["src_nhs_app"] }
```

`when` یک فهرست «همه باید برقرار باشند» (AND) است و داخل هر عضو می‌تواند `any_of` (OR) باشد. سه عملگر عددی هم وجود دارد: `branches_open_min/max` و `unanswered_min/max` که فقط در هشدارها و قواعد پوشش استفاده می‌شوند.

### ۲.۴ نگاشت شواهد

```json
{ "question_id": "q_pain_location", "option_id": "right_lower",
  "symptom_id": "s_pain_rlq", "state": "present" }
```

۵۵ نگاشت، ۲۵ نشانه از ۲۷ نشانه را پوشش می‌دهد. دو نشانه (`s_bladder_pressure`، `s_abdominal_cramp`) هیچ پرسشی ندارند و در نتیجهٔ نهایی صادقانه با برچسب **«خارج از پرسش‌نامه»** نشان داده می‌شوند، نه «ندارد».

## ۳) الگوریتم — دقیقاً چه اتفاقی می‌افتد

هیچ امتیاز، هیچ آستانهٔ احتمالی و هیچ مرتب‌سازی بر پایهٔ «شدت تطابق» وجود ندارد. کل منطق:

```text
nextQuestion():
  اگر پوشش = out_of_scope → null (توقف)
  اولین پرسشی در ترتیب ask_order که:
      قابل‌نمایش است (visibility) و پاسخ ندارد  → همان

answer(id, value):
  اعتبارسنجی مقدار بر اساس نوع پرسش
  اگر پرسش قابل‌نمایش نیست → QuestionNotVisible
  اگر جلسه متوقف شده → SessionStopped
  ثبت پاسخ + یک گام در تاریخچه (برای undo، حداکثر ۵۰ گام)

derive():
  1. pruneInvisible(): پاسخ پرسش‌هایی که دیگر قابل‌نمایش نیستند کنار گذاشته می‌شود
  2. matchedPaths(): برای هر مسیر، when را روی پاسخ‌های فعال بسنج → چند موضوع باز شد
     branchCount = تعداد موضوع‌های باز
  3. safety = همهٔ قواعد ایمنی که when آن‌ها برقرار است (مستقل از کارت‌ها)
  4. coverage = اولین قاعدهٔ پوشش که برقرار است، به ترتیب فایل:
       out_of_scope_pregnancy → no_pain_no_other → complete_no_match
       → no_branch → sufficient → (پیش‌فرض: insufficient)
  5. stopped = (coverage == out_of_scope)

result():
  cards_allowed = (coverage == "sufficient")
  conditions = موضوع‌های باز، به ترتیب بستهٔ دانش (نه رتبه!)
  evidence[condition] = هفت گروه: present / absent / unknown /
                        not_reported / not_asked / not_covered / conflict
  safety همیشه برمی‌گردد، حتی وقتی هیچ کارتی مجاز نیست
```

چهار تصمیم طراحی که باید بدانی:

1. **«نپرسیده» با «خیر» یکی نیست.** پرسشی که نمایش داده نشده، در هیچ قاعده‌ای «خیر» حساب نمی‌شود.
2. **«نمی‌دانم» هیچ شرط مثبتی را برآورده نمی‌کند** و در شواهد گروه جداگانه دارد.
3. **هشدار ایمنی از نتیجه جدا است.** حتی وقتی پوشش کافی نیست و هیچ کارتی نشان داده نمی‌شود، هشدار فوری نمایش داده می‌شود.
4. **پوشش، دروازهٔ نمایش است.** با باز شدن یک مسیر `sufficient` می‌شود؛ اما رابط صفحهٔ نتیجه را فقط در پایان پرسش‌ها نشان می‌دهد. (این نکته در بخش ۹ به‌عنوان یک ضعف ثبت شده: موتور از پرسش دوم به بعد «نتیجه» دارد، ولی کاربر تا انتها می‌رود.)

### ۳.۱ «تشخیص» چرا کنار گذاشته شده

- خروجی فقط **نام موضوع** + **دلیل** + **گروه‌بندی شواهد** است؛ کلمهٔ احتمال/درصد/امتیاز در متن‌ها ممنوع است و آزمون خودکار وجود چنین واژه‌هایی را در بخش نتیجه رد می‌کند.
- اگر دو موضوع باز شود، هر دو با دلیل خودشان نمایش داده می‌شوند و سیستم نمی‌گوید کدام محتمل‌تر است.
- در بارداری یا احتمال بارداری، ابزار **متوقف** می‌شود و فقط ارجاع فوری می‌دهد.
- متن پایانی همیشه می‌گوید این‌ها «موضوع برای بررسی» هستند، نه تشخیص.

- **نامعلوم:** تب

### ۵.۱ همان مسیر به شکل درخت

```text
q_pain_present?
├── خیر ────────────────► مسیر بی‌درد (پرسش ادراری/اسهال/تب) ─► اغلب insufficient
├── نمی‌دانم ───────────► مثل «بله» ادامه می‌دهد، ولی هیچ شرط مثبتی را برنمی‌آورد
└── بله
    └── q_pain_location?
        ├── پایین راست ──► [app باز شد]  ◄── همین‌جا پوشش sufficient می‌شود
        ├── اطراف ناف ───► [app باز شد] (مسیر p_app_periumbilical)
        ├── پهلو/کمر ────► [kidney_stone]
        └── چند ناحیه ───► هنوز هیچ مسیری؛ ادامهٔ پرسش‌ها
    ادامه: انتشار؟ تب؟ ادرار؟ اسهال؟ شدت؟ حرکت؟
        └── هر پاسخ فقط وضعیت شواهد را عوض می‌کند، نه باز/بسته بودن مسیر
```

نکتهٔ کلیدی: **درخت واقعی نیست.** مسیرها موازی و مستقل‌اند؛ فقط *ترتیب پرسش* خطی است. یعنی یک پاسخ می‌تواند هم‌زمان دو مسیر باز کند و هیچ پاسخی مسیر دیگری را نمی‌بندد (مگر با قاعدهٔ صریح).

| ۸ | `q_associated_symptoms` | تهوع + استفراغ | kidney_stone |
| ۹ | `q_urinary_symptoms` | خون در ادرار + تکرر | kidney_stone |
| ۱۰ | `q_flank_radiation` | بله | **kidney_stone + urinary_tract** |
| ۱۱ | `q_fever_chills` | نه | kidney_stone, urinary_tract |
| ۱۲ | `q_diarrhea_vomiting` | هیچ‌کدام | kidney_stone, urinary_tract |
| ۱۳ | `q_keep_fluids` | نمی‌دانم | kidney_stone, urinary_tract |
| ۱۴ | `q_dehydration_signs` | هیچ‌کدام | kidney_stone, urinary_tract |
| ۱۵ | `q_unbearable_pain` | نه | kidney_stone, urinary_tract |
| ۱۶ | `q_pregnancy_possible` | نه | kidney_stone, urinary_tract |

خروجی: **دو کارت** — سنگ کلیه (مسیر `p_stone_flank`) و عفونت مجاری ادراری (مسیر `p_uti_urinary`). عفونت کلیه باز نشد، چون قاعده‌اش تب/لرز همراه درد پهلو می‌خواهد.

این نمونه سه رفتار مهم را نشان می‌دهد:

1. **مسیرها موازی‌اند.** باز شدن یکی، دیگری را نمی‌بندد؛ به همین دلیل کارت ادراری هم می‌آید.
2. **تناقض برچسب می‌خورد.** در کارت سنگ کلیه، «استفراغ» هم از سؤال همراه (بله) و هم از سؤال اسهال/استفراغ («هیچ‌کدام») آمده، پس در گروه **«پاسخ متناقض»** می‌نشیند و رابط دکمهٔ «این دو پاسخ را اصلاح کنم» می‌دهد. سیستم هیچ‌کدام را حذف نمی‌کند.
3. **نشانهٔ بی‌پرسش.** «درد یا فشار ناحیهٔ مثانه» در کارت ادراری به‌عنوان **«خارج از پرسش‌نامه»** می‌آید، نه «ندارد».

### ۶.۱ همان مسیر به شکل درخت

```text
q_pain_location = پهلو/کمر  ──► p_stone_flank  ──► [سنگ کلیه]
q_flank_radiation = بله     ──► p_stone_flank  ──┐ (مسیر دوم به همان موضوع)
q_urinary_symptoms ⊇ {تکرر, خون} ──► p_uti_urinary ──► [عفونت ادراری]
q_fever_chills = بله + درد پهلو ──► p_kidney_infection ──► [عفونت کلیه]   ← این‌بار «نه» بود، باز نشد
```

یعنی «سنگ کلیه» دو مسیر ورودی دارد و «عفونت کلیه» ترکیب دو شرط می‌خواهد. این همان جایی است که در درخواست تو باید «سؤال متمرکزتر» شود: امروز هر دو موضوع با یک پرسش مشترک باز می‌شوند، فردا با گره‌های زنجیره‌ای می‌شود اول پهلو را باریک کرد، بعد تب را پرسید، بعد ادرار.

## ۷) آنچه کاربر روی صفحه می‌بیند (لایهٔ نمایش)

- **کارت راهنمای ربات** برای هر پرسش: توضیح محاوره‌ای + فهرست «اگر این‌طور است → این گزینه» + قاعدهٔ پایانی «اگر هیچ‌کدام نمی‌خورد → نمی‌دانم». متن‌ها در `ui/question-help.js` است و هیچ تصمیمی نمی‌گیرد.
- **نوار پیشرفت** بر پایهٔ «پاسخ‌داده‌شده از کل پرسش‌های **قابل‌نمایش**» — به همین دلیل عدد کل با تغییر پاسخ‌ها کم و زیاد می‌شود (این عمدی است).
- **کادر یادداشت آزاد** زیر گزینه‌ها: فقط حافظهٔ صفحه، بدون اثر روی موتور.
- **صفحهٔ نتیجه:** پوشش + هشدارها (بالاتر از کارت‌ها) + کارت‌ها با هفت گروه شواهد + فهرست یادداشت‌ها + دکمهٔ شروع دوباره/ویرایش پاسخ‌ها.
- **دسترس‌پذیری:** ناحیهٔ `aria-live` برای اعلام تغییر صفحه، `role="alert"` برای هشدار، متن کامل راهنما برای صفحه‌خوان، و احترام به `prefers-reduced-motion`.

## ۸) افزودن یک بیماری جدید — چک‌لیست کامل

فرض: می‌خواهی «کوله‌سیستیت (التهاب کیسهٔ صفرا)» اضافه شود. الان برای این کار **فقط داده کافی نیست**؛ این‌ها باید انجام شوند:

### گام ۱ — منبع

برای هر ادعای بالینی یک ورودی در `sources` بستهٔ دانش: `id`, `kind` (`clinical_guideline`/`internal_profile`)، `title_fa`, `publisher`, `url`, `accessed`. بدون `source_refs` هر بخش، آزمون ساختار رد می‌کند.

### گام ۲ — نشانه‌ها

`bundle.symptoms[]`: اگر نشانهٔ تازه‌ای لازم است (مثلاً «درد بعد از غذاهای چرب») اضافه کن: `{ "id": "s_pain_after_fatty_food", "label_fa": "…" }`. اگر نشانهٔ موجود کافی است، دوباره نساز.

### گام ۳ — پرسش‌ها (بخشی که بیشترین کار را دارد)

`bundle.questions[]` برای هر پرسش تازه:

- `id` تازه (پیشوند `q_`)
- `ask_order` **یکتا** و عدد صحیح ≥ ۱ (اگر می‌خواهی زودتر پرسیده شود، عدد بین موجودها بگیر)
- `type` یکی از `boolean3` / `single` / `multi` / `scale`
- `text_fa` و `why_fa` (هر دو اجباری)
- `source_refs`
- `visibility`: `always` یا `any_of` که **فقط به پرسش‌هایی با `ask_order` کوچک‌تر** ارجاع دهد
- گزینه‌ها: `boolean3` باید دقیقاً `yes/no/unknown` باشد؛ در `multi` گزینه‌های `none` و `unknown` باید `exclusive: true` داشته باشند؛ `scale` نیاز به `min/max` دارد
- اگر می‌خواهی «نمی‌دانم» داشته باشد، گزینه‌اش را با `id: "unknown"` بگذار

> **تلهٔ رایج:** `ask_order` تکراری یا وابستگی به پرسش بعدی → موتور در بارگذاری خطا می‌دهد و کل ابزار «متوقف شد» نشان می‌دهد.

### گام ۴ — موضوع

`bundle.conditions[]`:

- `id`, `name_fa`, `article_slug` (نامک مقالهٔ دانشنامه), `profile_ref` **باید `#` داشته باشد** (`disease-profiles.json#cholecystitis`)
- `link_status` یکی از `needs_live_verification` / `verified_published` / `unmapped`
- `symptom_links` **حداقل ۳ مورد**؛ هر مورد `symptom_id` (باید در `symptoms` باشد) + `profile_line` + `source_refs`
- `red_flag_refs` فقط شناسهٔ هشدارهای موجود در `safety_rules`
- `review_status`

### گام ۵ — مسیر (بدون مسیر، موضوع هرگز دیده نمی‌شود)

`bundle.paths[]` حداقل یک مسیر با `condition_id` این موضوع، `when` از پرسش/گزینه‌های موجود، `note_fa`، `source_refs`.
موتور در پایان اعتبارسنجی صریحاً می‌گوید: `condition X: no path can open it`.

### گام ۶ — هشدار و پوشش (اگر لازم است)

`bundle.safety_rules[]` برای نشانه‌های خطر (سطح `urgent`/`prompt`/`info`) و — در صورت نیاز — قاعدهٔ پوشش تازه. **ترتیب** قواعد پوشش معنا دارد (اولین تطابق برنده است).

### گام ۷ — دامنه

`bundle.scope.conditions_in_scope[]` را به‌روز کن و `bundle_version` را بالا ببر (`0.2.0-draft` → `0.3.0-draft`) و `change_notes` را بنویس.

### گام ۸ — نگاشت شواهد (جایی که بیشتر مردم فراموش می‌کنند)

`symptom-checker/engine/data/evidence-map.v1.json`:

- برای هر نشانهٔ موضوع جدید، حداقل یک ورودی `present` (و اگر ممکن است `absent`) با `question_id`/`option_id` معتبر
- **`bundle_version` داخل این فایل باید دقیقاً با بسته یکی باشد**، وگرنه موتور با `BundleValidationError` بالا نمی‌آید
- نشانه‌ای که نگاشت ندارد خطا نیست، ولی در نتیجه «خارج از پرسش‌نامه» می‌شود — پس عمداً انتخاب کن

### گام ۹ — متن راهنمای رابط

`symptom-checker/ui/question-help.js` برای هر پرسش تازه و **هر گزینه‌اش** یک جمله. (آزمون تازهٔ `ui/tests/question-help.test.js` این را اجباری می‌کند.)

### گام ۱۰ — سناریوها و انتظارات

- `docs/symptom-checker/phase-1/scenarios.v1.json` (۱۲ سناریو) و `docs/symptom-checker/phase-5/scenarios-adversarial.v1.json` (۱۳ سناریو): برای مسیر تازه حداقل یک سناریو با `branches_open` و `branches_must_not_open` بنویس.
- **همهٔ سناریوهای موجود را دوباره اجرا کن**: مسیر تازه می‌تواند در سناریوهای قدیمی هم باز شود و آن‌ها را بشکند. این انتظارات **دستی** نوشته شده‌اند، تولید خودکار ندارند.

### گام ۱۱ — دروازه‌ها

```sh

```

### گام ۱۲ — انتشار

`build_package.py` → zip تازه؛ اگر متن/کد عوض شده، نسخهٔ افزونه هم بالا می‌رود (`HJ_SC_VERSION` + هدر). سپس مستندسازی: جدول‌های گزارش فاز ۱، چنج‌لاگ، راهنمای انتشار. **داده‌ها داخل zip هستند؛ پس افزودن بیماری = انتشار نسخهٔ تازهٔ افزونه، نه فقط ویرایش فایل روی سایت.**

### ۸.۱ چه چیزهایی می‌شکنند (تجربهٔ همین مخزن)

| تغییر | چه چیزی می‌شکند |
|---|---|
| بالا بردن `bundle_version` | `evidence-map` (اگر هم‌گام نشود)، سناریوها، هر جایی که نسخه را چاپ می‌کند (`0.2.0-draft` در آزمون وردپرس هم بررسی می‌شود) |

## ۱۰) معماری پیشنهادی برای رسیدن به «زنجیره» (طرح، اجرا نشده)

خواستهٔ تو: هر بخش از یک زنجیره بتواند به زنجیرهٔ دیگر وصل شود، به مقصد دیگری برسد، سؤال‌ها قابل کپی و بازاستفاده باشند، و افزودن بیماری بدون شکستن سیستم باشد.

### ۱۰.۱ مدل «گره» به‌جای «پرسش با ترتیب ثابت»

```jsonc
// graph.steps[] — هر گره یک کار می‌کند و می‌گوید بعدش کجا
{
  "id": "step_abdomen_pain_start",
  "ask": "q_pain_present",                 // به یک پرسش موجود ارجاع می‌دهد (قابل کپی)
  "enter": ["cond_app", "cond_cholecystitis"],   // با ورود به این گره، این موضوع‌ها «کاندید» می‌شوند
  "next": [
    { "when": { "q_pain_present": ["yes"] }, "goto": "step_abdomen_location" },
    { "when": "else",                        "goto": "step_abdomen_no_pain" }
  ]
}
```

- **قابل کپی و بازاستفاده:** گره «سابقهٔ خانوادگی» یک بار نوشته می‌شود و هر بیماری که لازم دارد با `enter` به آن وصل می‌شود.
- **زنجیرهٔ نو به زنجیرهٔ موجود:** هر گره فقط `goto` می‌خواهد؛ مسیر قلب می‌تواند به گرهٔ گوارشی «درد سر دل» وصل شود.
- **تمرکز تدریجی:** هر `next` می‌تواند ناحیه را باریک‌تر کند؛ این همان «هر بار سؤال متمرکزتر» است.
- **بدون شکستن:** موضوع جدید فقط `enter` و چند `symptom_link` می‌خواهد؛ ساختار مسیرها دست نمی‌خورد.

### ۱۰.۲ ماژول‌های ورودی که امروز نداریم

| ماژول | داده | چرا |
|---|---|---|
| دموگرافیک | سن، جنس، بارداری | شرط نمایش/توقف و «سن پایین ⟹ مسیر قلبی کم‌رنگ‌تر» |
| ناحیه | کلیه، قلب، زانو، گردن، پوست، شکم، پهلو، تنفس، سردرد، چشم، گوش، سرگیجه | انتخاب بخش اصلی، همان چیزی که خواستی |
| سابقهٔ خانوادگی | بیماری + نسبت (پدر/مادر/خواهر/برادر/خانوادهٔ پدر/خانوادهٔ مادر) + «دیگری» متنی | فقط برای توضیح، نه امتیاز |
| دارو | فهرست نام‌ها | جست‌وجوی متن ساده روی فهرست دارو↔نشانه |

### ۱۰.۳ استدلال افتراقی بدون «تشخیص»

پیشنهاد: به‌جای امتیاز، سه نوع قاعدهٔ قابل‌مستندسازی:

1. **`shared_with`** — «این دو موضوع این نشانه‌ها را مشترک دارند» (همان نمودار مشترکات که خواستی؛ از داده تولید می‌شود، نه دستی).
2. **`favours`** — «اگر با گذشت زمان برطرف شد، الگو بیشتر با گوارش می‌خواند» (جملهٔ توضیحی، بدون احتمال).
3. **`excludes_if`** — «در نبود این نشانه‌ها و سن پایین، موضوع قلبی در این مرحله کنار گذاشته می‌شود» — با متن صریح «کنار گذاشتن در این مرحله، به معنی رد بیماری نیست».

نمودار پایانی می‌تواند از همین داده ساخته شود: دو موضوع، نشانه‌های مشترک در وسط، نشانه‌های اختصاصی در دو طرف، و پیام «اشتراک نشانه هرگز دلیل بیماری نیست؛ اثبات با پزشک و آزمایش».

### ۱۰.۴ فازبندی پیشنهادی

| فاز | کار | خروجی |
|---|---|---|
| ۶.۱ | schema v2 برای گراف گره‌ها + مترجم از بستهٔ فعلی (بدون تغییر رفتار) | موتور می‌تواند هر دو شکل را بخواند؛ ۸۱ آزمون باید بی‌تغییر بماند |
| ۶.۲ | ماژول دموگرافیک + ناحیه + مسیرهای زنجیره‌ای برای خوشهٔ شکم | همان ۵ موضوع، ولی با ترتیب پویا و ۲ پرسش کمتر |
| ۶.۳ | سابقهٔ خانوادگی + دارو (متنی) + قواعد `shared_with`/`favours`/`excludes_if` | توضیح افتراقی متنی |
| ۶.۴ | نمودار مشترکات (SVG از داده) + ابزار نویسندگی (پیش‌نمایش/اعتبارسنجی) | کاهش هزینهٔ افزودن بیماری |
| ۶.۵ | تولید خودکار انتظارات سناریو + دروازهٔ CI | افزودن بیماری بدون دست‌زدن به ۲۵ سناریو |

هر فاز باید با همان معیار امروز سنجیده شود: صفر تغییر در رفتار موضوع‌ها وقتی داده تغییر نکرده، و صفر ادعای بالینی تازه.

## ۱۱) مرزهای این سند

- هیچ‌کدام از این توصیف‌ها ادعای دقت بالینی یا ایمنی نیست؛ محتوا `pending_team_review` است.
- اعداد و نمونه‌ها از اجرای واقعی موتور و بستهٔ موجود در همین تاریخ آمده‌اند (قابل بازتولید با `node --test` و سناریوها).
- بخش ۱۰ **طرح** است، نه چیزی که ساخته شده باشد.
- رفتار مرورگر واقعی، موبایل، صفحه‌خوان و کش سایت هنوز بازبینی انسانی لازم دارد.

## ۱۲) به‌روزرسانی پس از فاز ۱ — لایهٔ v2 کنار v1

این سند وضعیت اجرایی امروز را توصیف می‌کند و آن وضعیت عوض نشده است: صفحه همان بستهٔ v1 را می‌خواند و رفتار همان است. چیزی که اضافه شده، **توانایی خواندن** شکل تازه است:

- **`docs/symptom-checker/schema/knowledge-bundle.v2.schema.json`** — شکل ماتریس بیماری × نشانه (schema `2.0.0`): کاتالوگ نشانه با شناسهٔ خوشه‌ای، نگاشت پاسخ→نشانه داخل هر گزینه، و `profile[]` با سطح.
- **`docs/symptom-checker/phase-1/knowledge-bundle.v2.json`** — همان بستهٔ امروز، در قالب تازه، تولیدشده با مبدل (نه دست‌نویس).
- **`symptom-checker/engine/src/adapter.js`** — تنها جایی که تفاوت دو شکل را می‌داند؛ موتور همچنان از یک شکل می‌خواند، پس نتیجه نمی‌تواند بین دو مسیر فرق کند.
- **اثبات:** هر ۲۵ سناریو و ۵۰۰۰ مسیر تصادفی با بستهٔ v2 همان `result()` را می‌دهند که در `tests/golden/v1/` قفل شده است.

جدول «چه چیزی می‌شکند» در بخش ۸ برای افزودن بیماری، از فاز ۳ به بعد کوتاه‌تر می‌شود؛ تا آن زمان مسیر رسمی همچنان همان مسیر v1 است. جزئیات: [گزارش فاز ۱](../phase-1/schema-v2-report.fa.md).
