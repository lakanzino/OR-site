## ۲. شکل v2 که واقعاً تولید شد

```
schema 2.0.0 · bundle symptom-checker.abdomen.v1 · bundle_version 0.2.0-draft
۲۷ نشانه (abd.*) · ۱۷ پرسش · ۷۱ گزینه · ۵۵ نگاشت پاسخ→نشانه
۵ بیماری با ۴۳ سطر پروفایل · ۶ override · ۱۰ منبع · ۸ قاعدهٔ ایمنی · ۵ قاعدهٔ پوشش
```

نمونهٔ واقعی از هر بلوک (بریده از فایل، بدون دست‌کاری):

```json
" symptoms[0] ": { "id": "abd.pain_abdomen", "legacy_id": "s_pain_abdomen",
                   "cluster": "abd", "label_fa": "درد شکم", "synonyms": ["دل‌درد", "درد معده"],
                   "category": "pain" }

" options[0] ": { "id": "yes", "label_fa": "بله",
                  "evidence": [{ "symptom_id": "abd.pain_abdomen", "state": "present" }] }

" profile[0] ": { "symptom_id": "abd.pain_abdomen", "level": "typical",
                  "profile_line": "درد ناگهانی که اغلب از اطراف ناف شروع می‌شود و سپس به پایین سمت راست شکم می‌رود",
                  "source_refs": ["src_profile_app", "src_nhs_app"] }
```

تصمیم‌های شکل‌دهی (همه در کد مبدل، نه در سند):

- **شناسه‌ها:** `s_pain_rlq` → `abd.pain_rlq`. پیشوند خوشه از یک ثابت (`abd` = شکم، پهلو و لگن) می‌آید و شناسهٔ قدیمی در `legacy_id` می‌ماند تا آداپتر از داده نگاشت کند، نه از حدس.
- **نگاشت پاسخ→نشانه داخل گزینه رفت و فایل بیرونی هم دست‌نخورده ماند.** هر دو تا اثبات هم‌ارزی کامل می‌مانند؛ v1 هیچ تغییری نکرد.
- **`level`:** v1 هیچ سطحی ندارد، پس هر سطر `typical` شروع می‌شود (قاعدهٔ رانبوک) — و همین حالا در داده ثبت است، نه اینکه بعداً استنتاج شود. مصرفش کار فازهای ۲–۴ است.
- **`overrides`:** همان `paths` فعلی، بی‌کم‌وکاست.
- **بلوک‌های بی‌تغییر:** `safety_rules`، `coverage_rules`، `sources`، `scope`، `disclaimers`، `answer_states`، `change_notes` عیناً منتقل شدند (آزمون برابری دارد).
- **متادیتای مهاجرت:** `migrated_from` و یک `migration_notes_fa` اضافه شد تا معلوم باشد این بسته از کجا آمده؛ هیچ ادعای بالینی تازه‌ای اضافه نشد.

## ۳. مبدل — قواعدی که در کد قفل است

`tools/symptom-checker-migrate/v1_to_v2.py`

- **ورودی دستی ممنوع:** تنها ورودی، `knowledge-bundle.v1.json` + `evidence-map.v1.json` است.
- **ایدمپوتنت و تکرارپذیر:** دو اجرا = بایت یکسان = همان SHA-256. `--check` اگر فایل کامیت‌شده کهنه باشد، خطا می‌دهد (آزمون دارد).
- **نگاشت قطعی:** `s_*` → `abd.*`، `symptom_links` → `profile` با `typical`، `paths` → `overrides`.
- **خطای صریح، نه خروجی ناقص:** اگر نگاشت شواهد به نشانه‌ای اشاره کند که وجود ندارد، مبدل با پیام متوقف می‌شود.

## ۴. اعتبارسنج — خطا و هشدار از هم جدا هستند

`tools/symptom-checker-migrate/validate_v2.py` فهرست `required` را **از خود فایل schema** می‌خواند، پس فیلدی که به سند اضافه شود، بی‌بررسی نمی‌ماند. نتیجهٔ اجرا روی بستهٔ کنونی:

```
WARNING symptom abd.abdominal_cramp: no option reports it (must show as not_covered, never absent)
WARNING symptom abd.bladder_pressure: no option reports it (must show as not_covered, never absent)
WARNING symptom abd.blood_stool: not in any condition profile
OK … schema 2.0.0 · bundle symptom-checker.abdomen.v1 0.2.0-draft — 27 نشانه، 17 پرسش، 5 بیماری، 6 override، 3 هشدار
```

این سه هشدار **درست** هستند و از v1 به ارث رسیده‌اند: دو نشانه هیچ پرسشی ندارند (باید `not_covered` نمایش داده شوند، نه «ندارد») و یک نشانه در پروفایل هیچ بیماری نیست. هیچ‌کدام را پاک نکردم؛ قانون «حذف فقط به‌خاطر نبود شاهد ممنوع» است.

چه چیزی **خطا** است: نشانهٔ ناشناس در شواهد، شناسهٔ تکراری، پروفایل بدون هیچ سطر `typical`، منبع ناشناس، نبود `review_status`، override روی بیماری ناموجود، ارجاع به پرسش/گزینهٔ ناموجود، ناهماهنگی نسخه، شناسهٔ بدون پیشوند خوشه، و **هر فیلد احتمال/امتیاز/وزن/اطمینان** در هر عمقی از داده.

اعتبارسنجی دوباره با موتور واقعی JSON Schema (Draft 2020-12) هم انجام شد: **۰ خطا**. این بررسی به‌صورت آزمون در `test_migrate.py` هست و اگر کتابخانه نصب نباشد، صریحاً `skip` می‌شود (نه اینکه بی‌صدا سبز شود).

## ۵. آداپتر — یک جا، نه پخش‌شده در موتور

`symptom-checker/engine/src/adapter.js`

| قاعده | چرا |
| --- | --- |
| شناسهٔ نشانه: `legacy_id` یا خودِ شناسه | نگاشت از داده می‌آید؛ نشانهٔ تازه بدون `legacy_id` هم کار می‌کند |
| `profile[]` → `symptom_links[]` (با حفظ ترتیب) | ترتیب، ترتیب شواهد در نتیجه را تعیین می‌کند؛ جابه‌جایی‌اش نتیجه را عوض می‌کند |
| `evidence[]` هر گزینه → نگاشت شواهد | همان ۵۵ سطر v1، این‌بار داخل خود بسته |
| `overrides` → `paths` | قواعدی که ماتریس بیانشان نمی‌کند |
| `level` حمل می‌شود، مصرف نمی‌شود | فاز ۱ فقط قالب را عوض می‌کند؛ اگر سطح روی نتیجه اثر می‌گذاشت، ادعای «رفتار تغییر نکرده» دروغ بود |

موتور v1 دست‌نخورده ماند به‌جز سه خط: تشخیص v2، ساخت شکل v1، و گزارش `schemaVersion` ورودی واقعی (`2.0.0` برای بستهٔ v2، `1.0.0` برای v1). ۱۲ آزمون تازه (`adapter.test.js`) همین‌ها را قفل می‌کند، از جمله: تغییر یک `state` در شواهد باید نتیجه را عوض کند (یعنی شواهد واقعاً خوانده می‌شوند، نه نادیده گرفته می‌شوند) و تغییر `level` نباید هیچ نتیجه‌ای را عوض کند.

## ۶. دروازهٔ عبور: هم‌ارزی بایت‌به‌بایت

`tools/symptom-checker-migrate/equivalence.mjs` سه کار می‌کند:

1. **برابری شواهد:** نگاشت بازساخته‌شده از v2 با `evidence-map.v1.json` مقایسه می‌شود — هم تعداد (۵۵) و هم **ترتیب به‌ازای هر نشانه** (چون ترتیب، ترتیب «از طریق این پاسخ‌ها» را در نتیجه می‌سازد).
2. **۲۵ سناریو:** پاسخ‌های ثبت‌شده در عکس طلایی به یک نشست v2 داده می‌شود و `result()` و `answers()` با فایل‌های `tests/golden/v1/scenarios/` مقایسه می‌شود.
3. **۵۰۰۰ مسیر تصادفی:** همان پاسخ‌های ثبت‌شده، این‌بار روی v2، مقابل `paths-5000-seed-5000.jsonl.gz`.

نتیجه:

```
OK schema 2.0.0 reproduces tests/golden/v1 exactly: 25 scenarios + 5000 random paths, 55 evidence rows
```

**اثبات اینکه دروازه گیرنده است:** یک `state` در دادهٔ v2 از `present` به `absent` عوض شد. دروازه همان‌جا ایستاد و محل را نام برد:

```
evidence s_fever at .0
  golden v1: "q_associated_symptoms.fever:present"
  v2 bundle: "q_associated_symptoms.fever:absent"
scenario sc05_pyelonephritis_pattern result at .conditions.1.evidence.present.0.symptom_id
```

فایل بازگردانده شد و `v1_to_v2.py --check` دوباره سبز شد.

## ۹.۱. CI تازه (حاکمیت دائمی رانبوک)

حاکمیت رانبوک می‌گوید همهٔ دروازه‌ها روی هر PR و شبانه روی سناریوهای تازه اجرا شوند؛ تا امروز هیچ CI در مخزن نبود. فایل `.github/workflows/symptom-checker-gates.yml` اضافه شد با سه کار:

| کار | چه چیزی | چه وقت |
| --- | --- | --- |
| `gates` | آزمون‌های پایتون (چهار مجموعه)، `validate_phase1`، `--check` مبدل، `validate_v2`، دروازهٔ هم‌نامی، `build --check`، بازرسی محرمانگی، ۹۳ آزمون موتور، ۱۷ آزمون رابط، دود ۱۲ سناریو، عکس طلایی، هم‌ارزی v2 | هر PR و push به `main` |
| `php` | `php-checks.mjs` با PHP واقعی در WebAssembly | هر PR |
| `wordpress` | `check-wordpress.mjs` روی ۶.۸.۳ و ۷.۱.۴ | هر PR |
| اجرای شبانه | همان‌ها + **هم‌ارزی تفاضلی روی ۵۰۰۰ مسیر تازه با seed زمانی** | `schedule` و اجرای دستی |

حالت تفاضلی تازه در `equivalence.mjs` (`--random --count --seed`) اضافه شد: مسیرهای تازه هم‌زمان روی v1 و v2 اجرا می‌شوند، پس چیزی که در ۵۰۰۰ مسیر قفل‌شده نبود هم پوشش می‌گیرد. همین حالت با `--count 300 --seed 12345` اجرا و سبز شد.

**اولین اجرای واقعی روی GitHub Actions، روی همین PR:** هر چهار کار سبز شد — `gates` ۱ دقیقه و ۲۳ ثانیه، `php` ۱۴ ثانیه، `wordpress 6.8.3` ۵۹ ثانیه و `wordpress 7.1.4` ۵۵ ثانیه (اجرای `41200536480`). پس این خط، ادعای کاغذی نیست: دروازه‌ها روی سرور GitHub هم همان نتیجهٔ محیط محلی را دادند.

## ۱۰. ریسک‌ها و چیزهایی که در این فاز عمداً انجام نشد

1. **`level` هنوز معنایی ندارد.** تا فاز ۴ هر سطر مثل قبل رفتار می‌کند؛ اگر کسی امروز SDK بخواهد، باید بداند `rare`/`not_expected` هیچ اثری ندارد.
2. **آداپتر نگاشت را از `legacy_id` می‌خواند.** اگر روزی کسی `legacy_id` را دستی پاک کند، شناسهٔ تازه در موتور می‌ماند و شواهد قدیمی (اگر بمانند) نمی‌خوانند؛ اعتبارسنج این حالت را خطا نمی‌داند چون برای نشانه‌های تازه لازم است. فاز ۳ (CLI) باید هنگام افزودن نشانهٔ تازه این را روشن کند.
3. **بستهٔ همراه همچنان v1 است.** یعنی سایت هنوز چیزی از ماتریس نمی‌بیند؛ این عمدی است (قانون افزایشی بودن).
4. **۰.۱.۵ آزمون مرورگری واقعی و نصب زنده ندارد** (بدهی همیشگی؛ فقط jsdom و وردپرس Playground).
5. **دو هشدار «نشانهٔ بدون پرسش»** باید در فاز ۶ تصمیم بگیرند: یا پرسش بگیرند یا برای همیشه `not_covered` بمانند.
6. **اجرای شبانه تا فردا شب نادیده است.** کار `schedule` از این پس هر شب اجرا می‌شود، ولی اولین اجرای شبانه در این نشست دیده نشده؛ فقط اجرای روی PR (همان کارها) سبز است.
