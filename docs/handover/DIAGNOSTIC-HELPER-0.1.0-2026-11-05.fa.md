# ابزار موقت تشخیصی: مرحله فقط‌خواندنی — ۵ نوامبر ۲۰۲۶

## درخواست و تصمیم دامنه

کارفرما ساخت ابزارهای تست و جمع‌آوری اطلاعات را تأیید کرد. پیشنهاد مشاور ترکیبی از تشخیص، درج رأی مصنوعی، ویرایش رأی و شبیه‌سازی نوبت در محیط زنده بود. در گام اول فقط افزونه مستقل `hj-diagnostic-helper` با خروجی JSON metadata ساخته شد. کد، دیتابیس و نصب اصلی سایت را ایجنت تغییر نمی‌دهد؛ نصب آن صرفاً در اختیار کارفرما و پس از بررسی و پشتیبان است. گزارهٔ «ریسک صفر» صحیح نیست: فعال‌سازی در خود وردپرس فهرست افزونه‌های فعال را تغییر می‌دهد و سایر هوک‌ها یا فیلترها می‌توانند در همان درخواست عملیات کنند. تزریق نمونه، تغییر وضعیت، پاکسازی رأی، شبیه‌سازی بازدید یا نوبت در این ابزار پیاده نشده است. تست‌های نوشتنی فقط روی DB کاملاً دورریختنی اجرا شده‌اند.

## خروجی و محدودیت‌ها

صفحه `ابزارها ← گزارش تشخیصی رأی` فقط برای `manage_options` و درخواست GET است؛ JSON را در textarea فقط‌خواندنی برای کپی ارائه می‌کند و هیچ API عمومی، فراخوانی شبکه، فرم ارسال، write SQL، activation hook، ذخیره option اختصاصی، ایجاد جدول یا دکمه تغییر ندارد. از پل فعلی جدول قابل‌شناسایی را می‌گیرد، نام جدول را با allowlist محدود اعتبارسنجی می‌کند و `SHOW COLUMNS` و `SHOW INDEX` انجام می‌دهد؛ خطای DB/exception به نامعلوم بدل و حالت suppress_errors پس از کار برگردانده می‌شود. جدول واقعی و پیشوند، مقادیر enum/set، default، توضیحات و خطاها نمایش داده نمی‌شوند.

گزارش شامل نام ستون‌ها، نوع سادهٔ بدون literals، nullable و key marker، نگاشت نقش‌های id/doctor/rating/status و ستون‌های PK در ترتیب است؛ `null` یعنی نامعلوم. این خروجی هیچ ردیف، شناسه شخص/پزشک، متن رأی، IP یا متای پزشک را از جدول رأی نمی‌خواند، اما نام ستون‌ها می‌توانند ساختار داخلی را نشان دهند و پیش از اشتراک باید بازبینی شوند. مقدارهای واقعی status و شمار رأی‌ها عمداً بررسی نشده‌اند. فیلترهای پل و hookهای بیرونی تحت کنترل این ابزار نیستند.

## آزمون و تحویل

- PHP WASM stub: نام نامعتبر جدول، خطا و استثنا، بازگرداندن suppression، کلید مرکب و ترتیب آن، مخفی‌بودن literals/default/errors/prefix.
- WP دورریختنی 6.8.3/PHP 8.3 و 7.1.4/PHP 8.4 با SQLite؛ همچنین نسخه افزونه اصلی ۰٫۳٫۱۲ در WP 7.1.4/PHP 8.4 جداگانه آزموده شد. نقش مدیر/ناشناس/مشترک/پزشک و POST، no form، عدم خواندن secret و رأی مصنوعی، عدم اجرای write SQL توسط گزارش، escaping نام مصنوعی شبیه HTML و حفظ رأی fixture موفق بود. ثبت تست و نقش‌ها فقط روی DB دورریختنی است.
- HTTP واقعی روی WP 7.1.4/PHP 8.4/SQLite دورریختنی با ZIP استخراج‌شده و افزونه اصلی ۰٫۳٫۱۲: مدیر GET با 200، header عدم کش و JSON قابل‌خواندن؛ POST مدیر 405، مشترک 403 و ناشناس 302 به ورود. ابتدا رد POST از داخل callback پس از شروع HTML باعث HTTP 200 شد؛ گارد به hook `load-*` پیش از خروجی منتقل شد و آزمون مجدد موفق بود. فرایند متوقف شد. بار واقعی و رفتار همه فیلترهای زنده تست نشده است.
- workflow MariaDB 11.4 دورریختنی در GitHub با هر دو حالت نسخه اصلی نصب‌شده ۰٫۳٫۱۲ و نسخه کاری روی commit قبلی `090eee4` موفق شد؛ اصلاح گارد متد بعداً افزوده شد و CI نسخه نهایی باید جداگانه بررسی شود. از داده سایت/بکاپ واقعی برای آزمون استفاده نشده است.
- بسته `releases/hj-diagnostic-helper-0.1.0.zip` فقط یک فایل runtime دارد و تست‌ها و harnessها را شامل نمی‌شود. SHA256 `f01a7abaa00b2c3de55741c101296ca11b623d63929dfffe5da7a8f29ba0c8de`؛ تطبیق فایل با سورس بررسی شده است. برای تصمیم نصب و نسخه نهایی، CI و بازبینی باید جداگانه تأیید شوند.

ساخت نمونه‌های رأی، مدیریت تأیید/رد، آمار و نوبت‌گیری از این مرحله جدا هستند. شناسه ملی و تلفن واقعی نباید در داده‌های آزمایشی یا چت وارد شوند. قبل از ساخت هر عملیات واقعی نیاز به طراحی دسترسی، حفظ داده، اثر در آمار/کش، audit، بازگردانی، جلوگیری از انتشار نمونه به عنوان تجربهٔ واقعی و توافق مرحله‌ای است.
